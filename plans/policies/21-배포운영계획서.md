## 1. 문서 개요

### 1.1 목적

본 배포 운영 계획서는 BlockPick 플랫폼의 안정적이고 효율적인 배포 및 운영을 위한 전략, 프로세스, 도구를 정의합니다. 고가용성, 확장성, 보안을 보장하면서 빠르고 안전한 배포를 가능하게 하는 것을 목표로 합니다.

### 1.2 범위

본 계획서는 다음을 포함합니다:

- **배포 전략**: Blue-Green, Canary, Rolling 배포
- **CI/CD**: 지속적 통합 및 배포 파이프라인
- **인프라**: AWS 기반 클라우드 아키텍처
- **모니터링**: 애플리케이션 및 인프라 모니터링
- **장애 대응**: 인시던트 관리 및 복구
- **보안**: 보안 운영 및 컴플라이언스
- **최적화**: 성능 및 비용 최적화

### 1.3 대상 독자

- **DevOps 팀**: 인프라 구축 및 배포 자동화
- **개발 팀**: CI/CD 파이프라인 활용
- **SRE (Site Reliability Engineers)**: 시스템 신뢰성 관리
- **운영 팀**: 일상적인 운영 및 모니터링
- **보안 팀**: 보안 정책 적용 및 감사

### 1.4 용어 정의

**CI/CD (Continuous Integration/Continuous Deployment)**: 지속적 통합 및 배포

**Blue-Green Deployment**: 두 개의 동일한 환경(Blue, Green)을 유지하고 전환하는 배포 방식

**Canary Deployment**: 일부 사용자에게만 먼저 배포하여 검증 후 전체 배포하는 방식

**Rolling Deployment**: 점진적으로 인스턴스를 교체하며 배포하는 방식

**IaC (Infrastructure as Code)**: 인프라를 코드로 관리

**APM (Application Performance Monitoring)**: 애플리케이션 성능 모니터링

**SLA (Service Level Agreement)**: 서비스 수준 협약

**SLO (Service Level Objective)**: 서비스 수준 목표

**SLI (Service Level Indicator)**: 서비스 수준 지표

## 2. 배포 전략

### 2.1 배포 전략 개요

BlockPick은 서비스의 특성과 변경의 위험도에 따라 적절한 배포 전략을 선택합니다.

### 2.2 Blue-Green Deployment

**개념**: 동일한 두 환경 (Blue, Green)을 유지하고, 새 버전을 Green에 배포한 후 트래픽을 전환

**장점**:
- 빠른 롤백 (트래픽만 다시 전환)
- 다운타임 제로
- 철저한 테스트 가능 (Green 환경에서)

**단점**:
- 인프라 비용 2배
- 데이터베이스 마이그레이션 복잡

**적용 대상**:
- 프로덕션 메인 배포
- 대규모 변경 사항
- Critical 서비스

**프로세스**:
1. Green 환경에 새 버전 배포
2. Green 환경 헬스 체크
3. Green 환경에서 Smoke 테스트
4. 로드 밸런서를 Green으로 전환
5. Blue 환경을 대기 상태로 유지 (롤백용)
6. 24시간 후 문제 없으면 Blue 환경 업데이트

### 2.3 Canary Deployment

**개념**: 신규 버전을 소수의 사용자(예: 5%)에게먼저 배포하여 검증 후 점진적 확대

**장점**:
- 위험 최소화
- 실제 사용자 피드백 조기 확보
- 문제 발생 시 영향 범위 제한

**단점**:
- 배포 시간 증가
- 복잡한 트래픽 라우팅 필요

**적용 대상**:
- 새로운 기능 출시
- 알고리즘 변경
- UI/UX 변경

**프로세스**:
1. 5% 트래픽을 Canary 서버로 라우팅
2. 메트릭 모니터링 (에러율, 응답 시간)
3. 문제 없으면 30분 후 25%로 증가
4. 50% → 100% 점진적 확대
5. 각 단계마다 메트릭 확인

### 2.4 Rolling Deployment

**개념**: 인스턴스를 하나씩 또는 소그룹씩 점진적으로 교체

**장점**:
- 추가 인프라 불필요
- 단순한 구현

**단점**:
- 배포 중 두 버전 공존
- 롤백 시간 오래 걸림

**적용 대상**:
- 스테이징 환경
- 마이너 버그 픽스
- 리스크 낮은 변경

### 2.5 배포 일정

**정기 배포**:
- **프로덕션**: 화요일, 목요일 오후 2시 (한국 시간)
- **스테이징**: 매일 (자동 배포)

**긴급 배포 (Hot-fix)**:
- Critical 버그 발견 시 즉시
- 승인: DevOps Lead + CTO
- 배포 후 사후 검증

**배포 금지 시간**:
- 금요일 오후 (주말 대응 방지)
- 공휴일 전날
- 트래픽 피크 시간 (오후 6-9시)

## 3. CI/CD 파이프라인

### 3.1 CI/CD 도구

**플랫폼**: GitHub Actions

**이유**:
- GitHub과 네이티브 통합
- 무료 플랜 충분 (월 2,000분)
- YAML 기반 간편한 설정
- 풍부한 Marketplace Actions

### 3.2 CI 파이프라인 (Pull Request)

```yaml
name: CI

on:
  pull_request:
    branches: [main, develop]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - Checkout 코드
      - Node.js 설치
      - 의존성 설치
      - ESLint 실행
      - Prettier 체크

  test:
    runs-on: ubuntu-latest
    steps:
      - Checkout 코드
      - Node.js 설치
      - 의존성 설치
      - 단위 테스트 실행 (Jest)
      - 커버리지 리포트 생성
      - Codecov 업로드

  security-scan:
    runs-on: ubuntu-latest
    steps:
      - Checkout 코드
      - Snyk 스캔 실행
      - 취약점 리포트

  build:
    runs-on: ubuntu-latest
    steps:
      - Checkout 코드
      - Docker 이미지 빌드
      - 이미지 태그: pr-<number>
      - ECR에 푸시
```

**실행 시간**: 5-7분

**성공 조건**: 모든 job 통과

**실패 시**: PR 병합 불가, 개발자에게 알림

### 3.3 CD 파이프라인 (Staging)

```yaml
name: Deploy to Staging

on:
  push:
    branches: [develop]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - Checkout 코드
      - 빌드 및 테스트 (CI 파이프라인 재사용)
      - Docker 이미지 빌드 (태그: develop-<sha>)
      - ECR 푸시
      - ECS 태스크 정의 업데이트
      - ECS 서비스 업데이트 (Rolling Deployment)
      - 배포 완료 대기
      - 헬스 체크
      - Slack 알림: 배포 완료
```

**트리거**: develop 브랜치에 push

**자동화**: 100% 자동, 승인 불필요

**실행 시간**: 10-15분

### 3.4 CD 파이프라인 (Production)

```yaml
name: Deploy to Production

on:
  push:
    branches: [main]

jobs:
  build-and-test:
    # CI 파이프라인과 동일

  deploy-approval:
    needs: build-and-test
    runs-on: ubuntu-latest
    steps:
      - 수동 승인 대기 (GitHub Environment)

  deploy-blue-green:
    needs: deploy-approval
    runs-on: ubuntu-latest
    steps:
      - Docker 이미지 빌드 (태그: v<version>)
      - ECR 푸시
      - Green 환경에 배포
      - Green 헬스 체크
      - Smoke 테스트 실행
      - 로드 밸런서를 Green으로 전환
      - Blue 환경 대기 상태 유지
      - Slack 알림: 프로덕션 배포 완료
```

**트리거**: main 브랜치에 push (릴리스)

**승인**: DevOps Lead 수동 승인 필수

**실행 시간**: 20-30분

**롤백**: Blue로 트래픽 다시 전환 (1분 이내)

### 3.5 Database Migration

데이터베이스 마이그레이션은 애플리케이션 배포와 별도로 관리합니다.

**도구**: Sequelize Migrations (Node.js ORM)

**프로세스**:
1. 마이그레이션 스크립트 작성 (up/down)
2. 스테이징에서 먼저 실행 및 검증
3. 프로덕션 배포 전 수동 실행
4. Backward Compatible 마이그레이션 우선
   - 컬럼 추가는 NULL 허용
   - 컬럼 삭제는 2단계 (사용 중지 → 삭제)
5. 마이그레이션 실패 시 롤백 스크립트 실행

**안전장치**:
- 마이그레이션 전 데이터베이스 백업
- Dry-run 모드로 먼저 테스트
- 트랜잭션 사용 (가능한 경우)

## 4. 인프라 아키텍처

### 4.1 클라우드 플랫폼

**주 플랫폼**: AWS (Amazon Web Services)

**리전**: ap-northeast-2 (서울)

**가용 영역**: ap-northeast-2a, ap-northeast-2c (Multi-AZ)

### 4.2 아키텍처 다이어그램

```
Internet
   ↓
CloudFront (CDN)
   ↓
Route 53 (DNS)
   ↓
Application Load Balancer
   ↓
ECS Fargate (Container)
   ├─ Backend API (Node.js)
   ├─ GraphQL Server
   └─ Blockchain Service
   ↓
RDS PostgreSQL (Multi-AZ)
   ↓
ElastiCache Redis (클러스터 모드)

S3 (정적 파일, 백업)
SQS (메시지 큐)
SNS (알림)
```

### 4.3 컴퓨팅 리소스

**ECS Fargate**:
- 서버리스 컨테이너 실행
- 자동 스케일링
- 태스크 정의: CPU 1 vCPU, Memory 2GB
- 서비스: Desired Count 2 (기본), Max 10

**Lambda**:
- 이벤트 드리븐 작업 (예: 이미지 리사이징)
- 배치 작업 (예: 일일 통계 집계)
- CloudWatch Events로 스케줄링

### 4.4 데이터베이스

**RDS PostgreSQL**:
- 버전: 15.x
- 인스턴스: db.t3.medium (프로덕션), db.t3.small (스테이징)
- Multi-AZ: 활성화 (고가용성)
- 자동 백업: 일일, 7일 보관
- Read Replica: 읽기 부하 분산 (필요시)

**ElastiCache Redis**:
- 버전: 7.x
- 노드: cache.t3.micro × 2 (클러스터 모드)
- 용도: 세션, 캐싱, 게임 상태

### 4.5 스토리지

**S3**:
- Bucket: blockpick-assets (이미지, 비디오)
- Bucket: blockpick-backups (데이터베이스 백업)
- Lifecycle Policy: 30일 후 Glacier로 이동

**EBS**: ECS 태스크 임시 스토리지

### 4.6 네트워킹

**VPC**:
- CIDR: 10.0.0.0/16
- Public Subnet: 10.0.1.0/24, 10.0.2.0/24
- Private Subnet: 10.0.11.0/24, 10.0.12.0/24

**Security Group**:
- ALB: 80, 443 허용 (모든 IP)
- ECS: ALB에서만 접근 허용
- RDS: ECS에서만 접근 허용

**NAT Gateway**: Private Subnet 인터넷 접근용

### 4.7 로드 밸런서

**Application Load Balancer (ALB)**:
- HTTPS 리스너 (포트 443)
- HTTP → HTTPS 리다이렉트
- 헬스 체크: /health 엔드포인트
- Sticky Session: 비활성화 (Stateless)

### 4.8 CDN

**CloudFront**:
- 정적 파일 캐싱 (이미지, CSS, JS)
- Edge Location: 글로벌
- SSL/TLS: AWS Certificate Manager
- Cache-Control: 이미지 7일, JS/CSS 1일

## 5. 배포 프로세스

### 5.1 스테이징 배포

**트리거**: develop 브랜치 push

**승인**: 불필요 (자동)

**절차**:
1. GitHub Actions CI/CD 파이프라인 자동 실행
2. 코드 빌드 및 테스트
3. Docker 이미지 빌드
4. ECR에 푸시
5. ECS 태스크 정의 업데이트
6. ECS 서비스 Rolling Update
7. 새 태스크 시작
8. 헬스 체크 통과 확인
9. 이전 태스크 종료
10. Slack 알림

**검증**:
- QA 팀이 스테이징 환경에서 테스트
- 통합 테스트 자동 실행

### 5.2 프로덕션 배포

**트리거**: main 브랜치 push (릴리스 태그)

**승인**: DevOps Lead 수동 승인

**절차**:
1. 릴리스 노트 작성 (CHANGELOG.md)
2. 버전 태그 생성 (v1.2.3)
3. main 브랜치에 병합
4. GitHub Actions 파이프라인 트리거
5. CI 단계 실행 (빌드, 테스트, 스캔)
6. 수동 승인 대기
7. Green 환경에 배포
8. Green 헬스 체크 (5분 대기)
9. Smoke 테스트 실행
10. 로드 밸런서를 Green으로 전환
11. 모니터링 집중 (30분)
12. Blue 환경 대기 상태 유지
13. Slack/Email 알림

**검증**:
- Smoke 테스트 통과
- 메트릭 정상 (에러율, 응답 시간)
- 24시간 모니터링

### 5.3 롤백 프로세스

**트리거 조건**:
- Critical 버그 발견
- 에러율 급증 (> 5%)
- 응답 시간 급증 (> 2초)
- 사용자 불만 다수

**Blue-Green 롤백**:
1. 문제 확인 및 승인 (DevOps Lead)
2. 로드 밸런서를 Blue로 다시 전환
3. 롤백 완료 (1분 이내)
4. Green 환경 종료
5. 사후 분석 (Post-mortem)

**Rolling 롤백**:
1. 이전 버전 이미지로 재배포
2. 10-15분 소요

**데이터베이스 롤백**:
- 마이그레이션 down 스크립트 실행
- 백업에서 복원 (최후의 수단)

## 6. 모니터링 및 알림

### 6.1 모니터링 도구

**Datadog**:
- APM (Application Performance Monitoring)
- 인프라 모니터링
- 로그 관리
- 대시보드 및 알림

**Sentry**:
- 에러 추적
- 스택 트레이스
- 사용자 영향 분석

**AWS CloudWatch**:
- AWS 리소스 모니터링
- 커스텀 메트릭
- 로그 수집

### 6.2 주요 메트릭

**애플리케이션 메트릭**:

| 메트릭 | 설명 | 임계값 | 알림 |
|--------|------|--------|------|
| 요청 수 | 초당 요청 수 | - | - |
| 응답 시간 | 평균 응답 시간 | > 500ms | Warning |
| 응답 시간 P95 | 95 백분위수 | > 1s | Critical |
| 에러율 | 5xx 에러 비율 | > 1% | Critical |
| Apdex | 사용자 만족도 | < 0.9 | Warning |

**인프라 메트릭**:

| 메트릭 | 설명 | 임계값 | 알림 |
|--------|------|--------|------|
| CPU 사용률 | ECS 태스크 CPU | > 80% | Warning |
| 메모리 사용률 | ECS 태스크 메모리 | > 85% | Warning |
| 디스크 사용률 | RDS 스토리지 | > 80% | Warning |
| DB 커넥션 | 활성 커넥션 수 | > 80% | Critical |
| Redis 메모리 | 메모리 사용률 | > 80% | Warning |

**비즈니스 메트릭**:

| 메트릭 | 설명 | 임계값 | 알림 |
|--------|------|--------|------|
| 회원가입 수 | 시간당 신규 가입 | < 10 | Warning |
| 게임 참여 수 | 시간당 참여 수 | < 50 | Warning |
| 결제 성공률 | 결제 성공 / 시도 | < 95% | Critical |
| API 가용성 | Uptime | < 99.9% | Critical |

### 6.3 대시보드

**실시간 대시보드**:
- 현재 활성 사용자 수
- API 응답 시간 (실시간 그래프)
- 에러율
- 인프라 헬스 (CPU, 메모리)
- 비즈니스 메트릭 (회원가입, 게임 참여, 결제)

**일일 리포트 대시보드**:
- 일일 활성 사용자 (DAU)
- 총 게임 참여 수
- 총 결제 금액
- 평균 응답 시간
- 에러 발생 건수

### 6.4 알림 설정

**알림 채널**:
- Slack: #alerts 채널 (실시간)
- PagerDuty: 온콜 엔지니어 (Critical만)
- Email: 개발팀 전체 (요약)

**알림 레벨**:

**Critical (즉시 대응 필요)**:
- 서비스 다운
- 에러율 > 5%
- 응답 시간 > 2s
- 데이터베이스 연결 실패
- 결제 실패율 > 10%

→ PagerDuty 호출, Slack 멘션, SMS

**Warning (모니터링 강화)**:
- 에러율 > 1%
- 응답 시간 > 500ms
- CPU/메모리 > 80%
- 디스크 공간 < 20%

→ Slack 알림

**Info (정보)**:
- 배포 완료
- 스케일링 이벤트
- 백업 완료

→ Slack 알림

## 7. 로깅 및 추적

### 7.1 로깅 전략

**로그 레벨**:
- **ERROR**: 즉시 조치 필요한 오류
- **WARN**: 잠재적 문제
- **INFO**: 중요한 이벤트 (로그인, 결제)
- **DEBUG**: 상세한 정보 (개발/스테이징만)

**로그 포맷**: JSON (구조화된 로그)

```json
{
  "timestamp": "2025-11-20T10:30:00Z",
  "level": "ERROR",
  "service": "api",
  "traceId": "abc123",
  "message": "Database connection failed",
  "error": { ... },
  "context": {
    "userId": "user123",
    "requestId": "req456"
  }
}
```

### 7.2 로그 수집 및 저장

**수집**: Datadog Agent (ECS 사이드카)

**저장**:
- Datadog Logs: 30일 보관
- S3: 장기 보관 (1년, 압축)

**검색**: Datadog Log Explorer

**알림**: 특정 패턴 탐지 시 알림

### 7.3 분산 추적 (Distributed Tracing)

**도구**: Datadog APM

**Trace ID**: 모든 요청에 고유 ID 부여

**Span**: 각 서비스 호출을 span으로 기록

**활용**:
- 느린 요청 분석
- 병목 지점 파악
- 마이크로서비스 간 호출 추적

### 7.4 로그 분석

**정기 분석**: 주간 에러 로그 리뷰

**자동 분석**: 머신러닝으로 이상 패턴 탐지

**액션**: 빈번한 에러는 이슈로 등록

## 8. 장애 대응

### 8.1 인시던트 관리 프로세스

**1단계: 탐지 (Detection)**
- 모니터링 알림
- 사용자 신고
- 헬스 체크 실패

**2단계: 대응 (Response)**
- 온콜 엔지니어 호출
- 인시던트 Slack 채널 생성
- 인시던트 지휘자 (Incident Commander) 지정

**3단계: 진단 (Diagnosis)**
- 로그 분석
- 메트릭 확인
- 최근 배포 확인
- 데이터베이스 상태 확인

**4단계: 복구 (Recovery)**
- 롤백 (배포 문제인 경우)
- 인프라 스케일링
- 데이터 복구
- 임시 우회 방법 적용

**5단계: 커뮤니케이션 (Communication)**
- 상태 페이지 업데이트 (status.blockpick.io)
- 사용자에게 공지 (앱 내 배너, 이메일)
- 이해관계자에게 보고

**6단계: 사후 분석 (Post-mortem)**
- 24시간 내 post-mortem 문서 작성
- 근본 원인 분석
- 재발 방지 액션 아이템
- 전체 팀에 공유

### 8.2 인시던트 심각도

**Severity 1 (Critical)**:
- 서비스 완전 다운
- 데이터 손실
- 보안 침해

대응: 즉시, 모든 리소스 투입

**Severity 2 (High)**:
- 주요 기능 불가 (게임 참여, 결제)
- 성능 심각한 저하

대응: 30분 내

**Severity 3 (Medium)**:
- 일부 기능 불가
- 소수 사용자 영향

대응: 4시간 내

**Severity 4 (Low)**:
- 사소한 문제
- 임시 우회 방법 있음

대응: 다음 배포에 포함

### 8.3 장애 시나리오별 대응

**데이터베이스 장애**:
- Read Replica로 읽기 전환
- 쓰기 작업 큐에 저장 후 복구 시 처리
- Multi-AZ Failover (자동)
- 백업에서 복구 (최악의 경우)

**ECS 태스크 실패**:
- Auto Scaling이 자동으로 새 태스크 시작
- 헬스 체크 실패 시 ALB가 트래픽 차단
- 모든 태스크 실패 시 롤백

**외부 서비스 장애 (PG사, 블록체인)**:
- 타임아웃 설정 (10초)
- Circuit Breaker 패턴 (3회 실패 시 차단)
- 사용자에게 안내 메시지
- 복구 시 재시도

## 9. 백업 및 복구

### 9.1 데이터베이스 백업

**자동 백업**:
- RDS Automated Backups: 일일, 7일 보관
- 백업 시간: 새벽 3시 (트래픽 최소)
- Point-in-Time Recovery: 5분 단위

**수동 스냅샷**:
- 주요 배포 전 수동 스냅샷
- 중요한 마일스톤 (월말, 분기말)

**백업 복구 테스트**:
- 월 1회 백업에서 복구 연습
- 복구 시간 측정 (RTO)

### 9.2 애플리케이션 데이터 백업

**S3 버킷**:
- Versioning 활성화
- Lifecycle Policy: 90일 후 Glacier
- Cross-Region Replication (재해 복구용)

**블록체인 데이터**:
- 블록체인 자체가 영구 기록
- 노드 데이터 정기 백업

### 9.3 재해 복구 계획 (DR)

**목표**:
- RPO (Recovery Point Objective): 1시간
- RTO (Recovery Time Objective): 4시간

**재해 시나리오**:
1. 서울 리전 전체 장애
2. 데이터센터 화재
3. DDoS 공격

**복구 절차**:
1. 다른 리전 (도쿄)에 인프라 구축
2. 최신 백업에서 데이터베이스 복구
3. S3 Cross-Region Replica 활용
4. DNS를 새 리전으로 전환
5. 서비스 재개

**DR 훈련**: 연 1회 실시

5. 근본 원인 분석 후 수정

**"데이터베이스 연결 실패"**:
1. RDS 콘솔에서 상태 확인
2. 커넥션 수 확인 (max 도달 시 kill)
3. Multi-AZ Failover 트리거 (필요 시)
4. Application 재시작

**"배포 후 에러율 급증"**:
