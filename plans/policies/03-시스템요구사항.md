## 1. 문서 개요

### 1.1 목적

본 문서는 BlockPick 플랫폼의 시스템 요구사항을 정의합니다. 시스템 아키텍처, 기술 스택, 성능 목표, 보안 요구사항, 인프라 구성 등 기술적 관점에서 시스템이 충족해야 할 요구사항을 명확히 합니다. 이 문서는 개발팀, 인프라팀, 보안팀이 시스템을 구축하고 운영하기 위한 기준이 됩니다.

### 1.2 범위

본 문서는 BlockPick 플랫폼을 구성하는 모든 시스템 컴포넌트를 다룹니다. 여기에는 모바일 애플리케이션, 백엔드 서버, 블록체인 시스템, 데이터베이스, 캐시, 스토리지, 모니터링 시스템 등이 포함됩니다. 각 컴포넌트의 기술 스택, 성능 목표, 보안 요구사항을 상세히 기술합니다.

### 1.3 대상 독자

본 문서의 주요 독자는 다음과 같습니다. 첫째, 백엔드 개발자는 서버 시스템을 구현할 때 참고합니다. 둘째, 프론트엔드 개발자는 모바일 애플리케이션을 개발할 때 활용합니다. 셋째, 블록체인 개발자는 스마트 컨트랙트와 블록체인 통합을 구현합니다. 넷째, 인프라 엔지니어는 서버 환경을 구축하고 관리합니다. 다섯째, 보안 담당자는 시스템의 보안성을 검토하고 강화합니다.

### 1.4 용어 정의

**Flutter**: 구글이 개발한 크로스 플랫폼 모바일 애플리케이션 프레임워크입니다. 하나의 코드베이스로 iOS와 Android 앱을 동시에 개발할 수 있습니다.

**Dart**: Flutter 애플리케이션 개발에 사용되는 프로그래밍 언어입니다.

**Riverpod**: Flutter 애플리케이션의 상태 관리를 위한 라이브러리입니다.

**GraphQL**: API 쿼리 언어로, 클라이언트가 필요한 데이터만 정확히 요청할 수 있도록 합니다.

**Polygon**: 이더리움 레이어 2 블록체인 네트워크로, 빠르고 저렴한 트랜잭션을 제공합니다.

**Web3dart**: Dart 언어로 이더리움 블록체인과 상호작용하기 위한 라이브러리입니다.

**PostgreSQL**: 오픈소스 관계형 데이터베이스 관리 시스템입니다.

**Redis**: 인메모리 데이터 저장소로, 캐싱과 세션 관리에 사용됩니다.

**AWS**: Amazon Web Services의 약자로, 클라우드 컴퓨팅 플랫폼입니다.

**Chainlink VRF**: 블록체인 상에서 검증 가능한 난수를 생성하는 서비스입니다.

**JWT**: JSON Web Token의 약자로, 인증 토큰 형식입니다.

**AES-256**: 고급 암호화 표준으로, 256비트 키를 사용하는 대칭 암호화 알고리즘입니다.

**SHA-256**: 256비트 해시 값을 생성하는 암호화 해시 함수입니다.

**LOD**: Level of Detail의 약자로, 화면에 표시되는 객체의 세부 수준을 조절하는 기법입니다.

## 2. 시스템 아키텍처 요구사항

### 2.1 전체 아키텍처 개요

BlockPick 시스템은 크게 세 개의 레이어로 구성됩니다. 첫 번째는 프레젠테이션 레이어로, 사용자와 직접 상호작용하는 모바일 애플리케이션입니다. 두 번째는 애플리케이션 레이어로, 비즈니스 로직을 처리하는 백엔드 서버입니다. 세 번째는 데이터 레이어로, 데이터베이스, 캐시, 블록체인이 포함됩니다.

모바일 애플리케이션은 Flutter 프레임워크로 개발되며, iOS와 Android를 모두 지원합니다. 애플리케이션은 GraphQL API를 통해 백엔드 서버와 통신하며, Web3dart 라이브러리를 사용하여 블록체인과 직접 통신합니다.

백엔드 서버는 GraphQL 서버로 구현되며, 사용자 인증, 게임 관리, Event Cash 관리, 알림 발송 등의 비즈니스 로직을 처리합니다. 서버는 PostgreSQL 데이터베이스에 데이터를 저장하고, Redis 캐시를 사용하여 성능을 최적화합니다.

블록체인 시스템은 Polygon 네트워크 상에 배포된 스마트 컨트랙트로 구성됩니다. 스마트 컨트랙트는 게임 참여 기록, 좌표 암호화 저장, 당첨자 선정 등 탈중앙화가 필요한 기능을 담당합니다. Chainlink VRF를 사용하여 공정한 난수를 생성합니다.

### 2.2 클라이언트-서버 통신

**SR-001: GraphQL API 사용**
모바일 애플리케이션과 백엔드 서버 간의 모든 통신은 GraphQL API를 통해 이루어져야 합니다. GraphQL은 클라이언트가 필요한 데이터만 요청할 수 있어 네트워크 트래픽을 최소화하고 성능을 향상시킵니다. 서버는 GraphQL 스키마를 정의하고, 쿼리와 뮤테이션을 통해 데이터를 제공합니다.

**SR-002: HTTPS 통신**
모든 API 통신은 HTTPS 프로토콜을 사용하여 암호화되어야 합니다. 이를 통해 중간자 공격을 방지하고, 데이터 전송 중 기밀성과 무결성을 보장합니다. 서버는 유효한 SSL/TLS 인증서를 사용해야 하며, 최소 TLS 버전 1.2 이상을 지원해야 합니다.

**SR-003: JWT 기반 인증**
사용자 인증은 JWT(JSON Web Token) 방식을 사용해야 합니다. 사용자가 로그인하면 서버는 액세스 토큰과 리프레시 토큰을 발급합니다. 액세스 토큰의 유효기간은 1시간이며, 리프레시 토큰의 유효기간은 30일입니다. 액세스 토큰이 만료되면 리프레시 토큰을 사용하여 새로운 액세스 토큰을 발급받습니다.

**SR-004: GraphQL 구독**
실시간 업데이트가 필요한 기능(예: 게임 참여자 수 실시간 업데이트, 채팅)은 GraphQL 구독(Subscription)을 사용해야 합니다. 구독은 WebSocket 프로토콜을 사용하여 서버와 클라이언트 간 양방향 통신을 제공합니다.

**SR-005: 요청 제한(Rate Limiting)**
서버는 과도한 요청으로부터 시스템을 보호하기 위해 요청 제한을 구현해야 합니다. 각 사용자는 분당 최대 60개의 요청을 보낼 수 있으며, 이를 초과하면 429 에러를 반환합니다. 요청 제한 정보는 응답 헤더에 포함되어야 합니다.

### 2.3 마이크로서비스 아키텍처 고려사항

현재 BlockPick은 모놀리식 아키텍처로 시작하지만, 향후 확장성을 위해 마이크로서비스로 전환할 수 있도록 설계되어야 합니다. 각 비즈니스 도메인(사용자 관리, 게임 관리, 결제 관리, 알림 관리 등)은 명확히 분리되어야 하며, 도메인 간 결합도를 최소화해야 합니다.

**SR-006: 도메인 주도 설계**
코드는 도메인 주도 설계(Domain-Driven Design) 원칙을 따라 구조화되어야 합니다. 각 도메인은 독립적인 모듈로 구성되며, 명확한 경계(Bounded Context)를 가져야 합니다. 이를 통해 향후 마이크로서비스로 분리할 때 최소한의 변경으로 전환할 수 있습니다.

**SR-007: API 게이트웨이**
클라이언트는 단일 진입점(API 게이트웨이)를 통해 백엔드 서비스에 접근해야 합니다. API 게이트웨이는 요청 라우팅, 인증, 로깅, 요청 제한 등의 공통 기능을 담당합니다. 초기에는 GraphQL 서버가 게이트웨이 역할을 하지만, 향후 독립적인 게이트웨이 서비스로 분리할 수 있습니다.

## 3. 모바일 애플리케이션 요구사항

### 3.1 플랫폼 지원

**SR-008: iOS 및 Android 지원**
모바일 애플리케이션은 iOS와 Android 플랫폼을 모두 지원해야 합니다. iOS는 최소 버전 13.0 이상, Android는 최소 API 레벨 21(Android 5.0 Lollipop) 이상을 지원해야 합니다. 이를 통해 대부분의 현역 기기에서 앱을 사용할 수 있습니다.

**SR-009: Flutter 프레임워크**
모바일 애플리케이션은 Flutter 버전 3.35.6을 사용하여 개발되어야 합니다. Flutter는 하나의 코드베이스로 iOS와 Android 앱을 동시에 개발할 수 있어 개발 효율성을 높이고, 유지보수 비용을 절감합니다. Dart 언어 버전 3.9.2를 사용합니다.

**SR-010: 화면 크기 대응**
애플리케이션은 다양한 화면 크기와 해상도를 지원해야 합니다. 스마트폰뿐만 아니라 태블릿에서도 정상적으로 동작해야 하며, 반응형 레이아웃을 사용하여 모든 기기에서 최적의 사용자 경험을 제공해야 합니다.

**SR-011: 다크 모드 지원**
애플리케이션은 라이트 모드와 다크 모드를 모두 지원해야 합니다. 시스템 설정에 따라 자동으로 테마가 전환되어야 하며, 사용자가 앱 내에서 수동으로 테마를 변경할 수도 있어야 합니다.

### 3.2 상태 관리

**SR-012: Riverpod 상태 관리**
애플리케이션의 상태 관리는 Riverpod 버전 2.6.1을 사용해야 합니다. Riverpod는 컴파일 타임 안전성을 제공하고, 테스트가 용이하며, 성능이 우수합니다. Provider 패턴을 사용하여 UI와 비즈니스 로직을 분리하고, 상태 변경을 효율적으로 관리합니다.

**SR-013: 불변 상태(Immutable State)**
모든 상태 객체는 불변(Immutable)으로 설계되어야 합니다. 상태를 변경할 때는 새로운 객체를 생성하여 대체합니다. 이를 통해 상태 변경을 추적하기 쉽고, 버그를 줄이며, 성능을 최적화할 수 있습니다.

**SR-014: 로컬 캐싱**
네트워크 요청 결과는 로컬에 캐싱되어야 합니다. 사용자가 오프라인 상태이거나 네트워크가 느린 경우에도 캐시된 데이터를 표시하여 사용자 경험을 유지합니다. 캐시는 적절한 만료 시간을 가져야 하며, 네트워크 복구 시 자동으로 업데이트됩니다.

### 3.3 그리드 렌더링

**SR-015: CustomPaint를 사용한 렌더링**
게임 화면의 1,000 곱하기 1,000 그리드는 Flutter의 CustomPaint 위젯을 사용하여 렌더링되어야 합니다. CustomPaint는 Canvas API를 제공하여 복잡한 그래픽을 효율적으로 그릴 수 있습니다. 각 블록은 직접 Canvas에 그려지며, 위젯 트리에 포함되지 않아 성능을 최적화합니다.

**SR-016: LOD(Level of Detail) 시스템**
그리드 렌더링은 LOD 시스템을 구현해야 합니다. 줌 레벨에 따라 블록의 세부 수준을 조절합니다. 멀리서 볼 때는 블록을 그룹화하여 단순하게 표시하고, 가까이서 볼 때는 개별 블록을 상세히 표시합니다. 이를 통해 렌더링 성능을 크게 향상시킵니다.

**SR-017: 60fps 유지**
그리드 화면은 항상 60fps를 유지해야 합니다. 사용자가 확대, 축소, 이동하는 동안에도 부드러운 애니메이션이 제공되어야 하며, 프레임 드롭이 발생하지 않아야 합니다. Flutter의 성능 프로파일링 도구를 사용하여 렌더링 성능을 지속적으로 모니터링하고 최적화합니다.

**SR-018: 제스처 인식**
그리드 화면은 멀티터치 제스처를 정확히 인식해야 합니다. 핀치 줌, 패닝(드래그), 싱글 탭, 더블 탭 등의 제스처가 자연스럽게 동작해야 합니다. 제스처 간 충돌을 방지하고, 사용자의 의도를 정확히 파악해야 합니다.

**SR-019: 미니맵 렌더링**
화면 우측 하단에 표시되는 미니맵은 전체 그리드를 축소하여 보여주어야 합니다. 미니맵은 현재 보고 있는 영역을 반투명 사각형으로 표시하며, 미니맵을 터치하면 해당 위치로 빠르게 이동합니다. 미니맵은 별도의 Canvas에 렌더링되어 메인 그리드와 독립적으로 업데이트됩니다.

### 3.4 블록체인 통합

**SR-020: Web3dart 라이브러리**
모바일 애플리케이션은 Web3dart 버전 2.7.3을 사용하여 블록체인과 통신해야 합니다. Web3dart는 Dart로 작성된 이더리움 클라이언트 라이브러리로, 스마트 컨트랙트 함수 호출, 트랜잭션 전송, 이벤트 리스닝 등의 기능을 제공합니다.

**SR-021: 지갑 생성 및 관리**
애플리케이션은 BIP39 표준에 따라 지갑을 생성하고 관리해야 합니다. 12개의 영어 단어로 이루어진 니모닉을 생성하며, 이로부터 개인키와 공개키를 유도합니다. 개인키는 기기의 안전한 저장소(iOS Keychain, Android Keystore)에 암호화되어 저장되어야 합니다.

**SR-022: 트랜잭션 서명**
모든 블록체인 트랜잭션은 클라이언트 측에서 서명되어야 합니다. 개인키는 절대로 서버로 전송되지 않으며, 모든 서명 작업은 기기 내에서 수행됩니다. 트랜잭션 서명 후 서명된 트랜잭션만 블록체인 네트워크로 전송됩니다.

**SR-023: 가스비 추정**
트랜잭션을 전송하기 전에 가스비를 추정하여 사용자에게 안내해야 합니다. Polygon 네트워크의 현재 가스 가격을 조회하고, 예상 가스비를 계산하여 사용자에게 표시합니다. 사용자가 가스비를 확인하고 승인한 후 트랜잭션을 전송합니다.

**SR-024: 트랜잭션 상태 모니터링**
트랜잭션을 전송한 후 블록체인에 포함될 때까지 상태를 모니터링해야 합니다. 트랜잭션 해시를 사용하여 주기적으로 상태를 조회하며, 대기 중, 처리 중, 성공, 실패 등의 상태를 사용자에게 표시합니다. 평균 10-20초 내에 트랜잭션이 확인됩니다.

### 3.5 로컬 데이터 저장

**SR-025: SQLite 데이터베이스**
애플리케이션은 로컬 데이터를 저장하기 위해 SQLite 데이터베이스를 사용해야 합니다. Sqflite 패키지를 사용하여 데이터베이스를 관리하며, 참여 내역, 통계, 설정 등을 저장합니다. 데이터베이스 스키마 버전을 관리하여 앱 업데이트 시 마이그레이션을 지원합니다.

**SR-026: Shared Preferences**
간단한 키-값 쌍 데이터는 Shared Preferences를 사용하여 저장해야 합니다. 사용자 설정, 토큰, 플래그 등을 저장하며, 빠른 읽기와 쓰기를 제공합니다.

**SR-027: 보안 저장소**
민감한 데이터(개인키, 토큰 등)는 Flutter Secure Storage를 사용하여 암호화된 형태로 저장해야 합니다. iOS에서는 Keychain, Android에서는 Keystore를 사용하여 운영 체제 수준의 보안을 제공합니다.

### 3.6 푸시 알림

**SR-028: Firebase Cloud Messaging**
푸시 알림은 Firebase Cloud Messaging(FCM)을 사용하여 구현되어야 합니다. FCM은 iOS와 Android를 모두 지원하며, 높은 전달률과 신뢰성을 제공합니다. 애플리케이션은 FCM 토큰을 서버에 등록하고, 서버는 이를 사용하여 알림을 발송합니다.

**SR-029: 포그라운드 및 백그라운드 알림 처리**
애플리케이션은 포그라운드, 백그라운드, 종료 상태 모두에서 푸시 알림을 수신하고 처리할 수 있어야 합니다. 포그라운드 상태에서는 인앱 알림으로 표시하고, 백그라운드 상태에서는 시스템 알림으로 표시합니다. 알림을 터치하면 해당 화면으로 딥 링크됩니다.

**SR-030: 알림 채널**
Android에서는 알림 채널을 사용하여 알림을 분류해야 합니다. 게임 알림, 당첨 알림, 프로모션 알림 등 각각의 채널을 생성하고, 사용자가 채널별로 알림을 제어할 수 있도록 합니다.

### 3.7 이미지 및 리소스 관리

**SR-031: 이미지 최적화**
애플리케이션에 포함되는 모든 이미지는 최적화되어야 합니다. PNG와 JPG 형식을 사용하며, 필요한 경우 WebP 형식을 사용하여 파일 크기를 줄입니다. 이미지는 여러 해상도로 제공되어 각 기기에 맞는 크기를 사용합니다.

**SR-032: 벡터 그래픽 사용**
아이콘과 로고는 가능한 벡터 그래픽(SVG)을 사용해야 합니다. 벡터 그래픽은 해상도에 관계없이 선명하게 표시되며, 파일 크기가 작습니다. Flutter에서는 flutter_svg 패키지를 사용하여 SVG를 렌더링합니다.

**SR-033: 리소스 지연 로딩**
화면에 즉시 필요하지 않은 리소스는 지연 로딩되어야 합니다. 애플리케이션 초기 로딩 시간을 단축하고, 메모리 사용을 최적화합니다. 이미지는 필요할 때만 로드되며, 캐싱을 통해 재사용됩니다.

### 3.8 에러 처리 및 로깅

**SR-034: 전역 에러 핸들러**
애플리케이션은 전역 에러 핸들러를 구현하여 모든 예외를 포착하고 적절히 처리해야 합니다. Flutter의 FlutterError.onError와 PlatformDispatcher.instance.onError를 사용하여 포착되지 않은 예외를 처리합니다. 중요한 에러는 로깅 서비스로 전송됩니다.

**SR-035: 로깅**
애플리케이션은 주요 이벤트와 에러를 로깅해야 합니다. Logger 패키지를 사용하여 로그 레벨(Debug, Info, Warning, Error)을 구분하고, 개발 환경과 프로덕션 환경에서 다른 로그 레벨을 사용합니다. 프로덕션 환경에서는 민감한 정보(비밀번호, 토큰 등)를 로깅하지 않습니다.

**SR-036: 크래시 리포팅**
애플리케이션은 Firebase Crashlytics를 사용하여 크래시를 모니터링하고 리포팅해야 합니다. 크래시 발생 시 스택 트레이스, 기기 정보, 사용자 액션 등을 자동으로 수집하여 서버로 전송합니다. 개발팀은 크래시 리포트를 분석하여 버그를 수정합니다.

### 3.9 앱 업데이트

**SR-037: 앱 버전 관리**
애플리케이션은 Semantic Versioning을 사용하여 버전을 관리해야 합니다. 버전 형식은 Major.Minor.Patch이며, 예를 들어 1.2.3입니다. Major 버전은 호환되지 않는 변경 시, Minor 버전은 새로운 기능 추가 시, Patch 버전은 버그 수정 시 증가합니다.

**SR-038: 강제 업데이트**
중요한 보안 패치나 필수 기능 변경이 있을 때, 애플리케이션은 사용자에게 강제 업데이트를 요구할 수 있어야 합니다. 앱 실행 시 서버로부터 최소 지원 버전을 조회하고, 현재 버전이 이보다 낮으면 업데이트 화면을 표시하고 앱 사용을 제한합니다.

**SR-039: 선택적 업데이트**
강제 업데이트가 아닌 경우, 사용자에게 새 버전이 있음을 알리고 선택적으로 업데이트하도록 유도합니다. 새로운 기능이나 개선 사항을 안내하며, "나중에" 옵션을 제공하여 사용자가 원할 때 업데이트할 수 있도록 합니다.

## 4. 백엔드 서버 요구사항

### 4.1 기술 스택

**SR-040: Node.js 런타임**
백엔드 서버는 Node.js 버전 18 이상에서 실행되어야 합니다. Node.js는 비동기 I/O를 효율적으로 처리하며, JavaScript/TypeScript 생태계의 풍부한 라이브러리를 활용할 수 있습니다.

**SR-041: TypeScript 사용**
서버 코드는 TypeScript로 작성되어야 합니다. TypeScript는 정적 타입 검사를 제공하여 런타임 에러를 줄이고, 코드 품질을 향상시킵니다. TypeScript 버전 5.0 이상을 사용합니다.

**SR-042: Apollo Server**
GraphQL 서버는 Apollo Server를 사용하여 구현되어야 합니다. Apollo Server는 GraphQL 사양을 완벽히 지원하며, 구독, 데이터 로더, 캐싱 등의 고급 기능을 제공합니다. Apollo Server 버전 4 이상을 사용합니다.

**SR-043: Express.js 통합**
Apollo Server는 Express.js 프레임워크와 통합되어야 합니다. Express는 미들웨어 시스템을 제공하여 요청 로깅, 에러 처리, CORS 설정 등을 쉽게 구현할 수 있습니다.

### 4.2 데이터베이스 연동

**SR-044: Prisma ORM**
데이터베이스와의 상호작용은 Prisma ORM을 사용해야 합니다. Prisma는 타입 안전한 쿼리를 제공하며, 데이터베이스 마이그레이션을 관리합니다. Prisma 스키마를 정의하면 TypeScript 타입이 자동으로 생성되어 개발 생산성을 높입니다.

**SR-045: 연결 풀링**
데이터베이스 연결은 풀링(Pooling)을 사용하여 관리되어야 합니다. Prisma는 내부적으로 연결 풀을 관리하며, 최소 연결 수는 10, 최대 연결 수는 50으로 설정합니다. 연결 타임아웃은 10초로 설정합니다.

**SR-046: 트랜잭션 관리**
여러 데이터베이스 작업이 원자적으로 수행되어야 하는 경우 트랜잭션을 사용해야 합니다. Prisma의 트랜잭션 API를 사용하여 일관성을 보장합니다. 예를 들어, 게임 참가 시 Event Cash 차감과 참여 기록 생성은 하나의 트랜잭션으로 처리됩니다.

### 4.3 캐싱

**SR-047: Redis 캐시**
자주 조회되는 데이터는 Redis에 캐싱되어야 합니다. 게임 목록, 사용자 프로필, 통계 등은 데이터베이스 대신 캐시에서 먼저 조회합니다. 캐시 미스(cache miss) 시에만 데이터베이스를 조회하고, 결과를 캐시에 저장합니다.

**SR-048: 캐시 무효화**
데이터가 업데이트되면 관련 캐시를 무효화해야 합니다. 예를 들어, 새로운 참여자가 게임에 참가하면 해당 게임의 캐시를 삭제합니다. 캐시 무효화 전략으로 TTL(Time To Live)과 이벤트 기반 무효화를 혼합 사용합니다.

**SR-049: 세션 저장**
사용자 세션 정보는 Redis에 저장되어야 합니다. JWT 리프레시 토큰, 로그인 상태, 임시 데이터 등을 Redis에 저장하여 빠른 조회와 만료 관리를 지원합니다.

### 4.4 인증 및 권한

**SR-050: JWT 토큰 발급**
사용자가 로그인하면 서버는 JWT 액세스 토큰과 리프레시 토큰을 발급해야 합니다. 토큰은 HMAC SHA-256 알고리즘으로 서명되며, 비밀키는 환경 변수로 관리됩니다. 액세스 토큰의 페이로드에는 사용자 ID, 이메일, 발급 시간, 만료 시간이 포함됩니다.

**SR-051: 토큰 검증 미들웨어**
모든 인증이 필요한 API 요청은 토큰 검증 미들웨어를 거쳐야 합니다. 미들웨어는 요청 헤더의 Authorization 필드에서 토큰을 추출하고, 서명을 검증하며, 만료 여부를 확인합니다. 유효한 토큰인 경우 사용자 정보를 컨텍스트에 추가합니다.

**SR-052: 리프레시 토큰 로테이션**
보안 강화를 위해 리프레시 토큰 로테이션을 구현해야 합니다. 리프레시 토큰을 사용하여 새 액세스 토큰을 발급할 때, 기존 리프레시 토큰을 무효화하고 새로운 리프레시 토큰도 함께 발급합니다. 이를 통해 토큰 탈취 시 피해를 최소화합니다.

**SR-053: 권한 기반 접근 제어**
일부 API는 특정 권한을 가진 사용자만 접근할 수 있어야 합니다. 예를 들어, 관리자 전용 API는 사용자의 role 필드를 확인하여 admin 권한이 있는지 검증합니다. 권한이 없으면 403 Forbidden 에러를 반환합니다.

### 4.5 블록체인 통합

**SR-054: Ethers.js 라이브러리**
서버는 Ethers.js 버전 6 이상을 사용하여 블록체인과 통신해야 합니다. Ethers.js는 이더리움 및 Polygon 블록체인과 상호작용하기 위한 완전한 라이브러리로, 스마트 컨트랙트 호출, 이벤트 리스닝, 트랜잭션 전송 등을 지원합니다.

**SR-055: 블록체인 노드 연결**
서버는 Polygon Amoy Testnet(초기 테스트) 및 Mainnet(프로덕션)에 연결되어야 합니다. Infura, Alchemy, QuickNode 등의 노드 프로바이더를 사용하며, 장애 대비를 위해 복수의 프로바이더를 설정합니다. 주 프로바이더 실패 시 자동으로 백업 프로바이더로 전환됩니다.

**SR-056: 이벤트 리스너**
서버는 스마트 컨트랙트에서 발생하는 이벤트를 실시간으로 수신해야 합니다. 예를 들어, GameFinalized 이벤트가 발생하면 서버는 이를 감지하고 당첨자 정보를 데이터베이스에 저장하며, 푸시 알림을 발송합니다. 이벤트 리스너는 블록체인 재구성(reorganization)에 대비하여 일정 수의 확인(confirmation)을 기다립니다.

**SR-057: 관리자 지갑**
서버는 특정 블록체인 작업(예: 게임 종료, 당첨자 선정)을 수행하기 위한 관리자 지갑을 가져야 합니다. 관리자 지갑의 개인키는 AWS Secrets Manager나 HashiCorp Vault와 같은 보안 저장소에 암호화되어 저장되며, 절대로 코드에 하드코딩되지 않습니다.

### 4.6 결제 시스템 연동

**SR-058: PG사 연동**
Event Cash 충전을 위해 국내 주요 PG사(Payment Gateway)와 연동되어야 합니다. 토스페이먼츠, 나이스페이, KG이니시스 등을 지원하며, 신용카드, 계좌이체, 간편결제 등 다양한 결제 수단을 제공합니다.

**SR-059: 웹훅 처리**
PG사로부터 결제 결과를 웹훅으로 수신해야 합니다. 웹훅 엔드포인트는 PG사의 서명을 검증하여 위조된 요청을 거부합니다. 결제 승인 시 사용자의 Event Cash를 충전하고, 거래 내역을 데이터베이스에 기록합니다.

**SR-060: 결제 재시도**
결제 실패 시 자동 재시도 로직을 구현해야 합니다. 일시적인 네트워크 오류로 인한 실패는 최대 3회까지 재시도하며, 재시도 간격은 지수 백오프(exponential backoff) 방식을 사용합니다.

**SR-061: 환불 처리**
사용자가 환불을 요청하거나 거래 취소가 필요한 경우, 서버는 PG사 API를 통해 환불을 처리해야 합니다. 환불 시 Event Cash를 차감하고, 환불 내역을 기록합니다. 이미 사용된 캐시는 환불할 수 없음을 사용자에게 안내합니다.

### 4.7 알림 발송

**SR-062: Firebase Admin SDK**
푸시 알림 발송은 Firebase Admin SDK를 사용해야 합니다. 서버는 사용자의 FCM 토큰을 데이터베이스에 저장하며, 이벤트 발생 시 해당 토큰으로 알림을 발송합니다.

**SR-063: 알림 큐**
대량의 알림을 발송할 때는 메시지 큐를 사용하여 비동기적으로 처리해야 합니다. BullMQ 등의 큐 시스템을 사용하며, Redis를 백엔드로 사용합니다. 알림 작업은 큐에 추가되고, 워커 프로세스가 순차적으로 처리합니다.

**SR-064: 알림 템플릿**
알림 메시지는 템플릿 시스템을 사용하여 관리되어야 합니다. 알림 유형별로 템플릿을 정의하고, 변수(예: 사용자 이름, 게임 이름, 상금)를 삽입하여 개인화된 메시지를 생성합니다.

**SR-065: 알림 실패 처리**
알림 발송 실패 시 재시도 로직을 구현해야 합니다. FCM 토큰이 만료되었거나 유효하지 않은 경우, 해당 토큰을 데이터베이스에서 제거합니다. 일시적인 네트워크 오류는 재시도합니다.

### 4.8 배치 작업

**SR-066: 스케줄러**
정기적으로 실행되어야 하는 작업(예: 게임 종료, 통계 집계)은 스케줄러를 사용하여 자동화되어야 합니다. Node-cron이나 Agenda 같은 라이브러리를 사용하며, cron 표현식으로 실행 시간을 정의합니다.

**SR-067: 게임 종료 작업**
매일 또는 주기적으로 종료 시간이 도래한 게임을 자동으로 종료하는 배치 작업이 실행되어야 합니다. 작업은 Chainlink VRF를 호출하여 난수를 생성하고, 이를 기반으로 당첨 블록을 선정하며, 결과를 블록체인과 데이터베이스에 기록합니다.

**SR-068: 통계 집계**
사용자별, 게임별 통계는 실시간으로 계산하기보다 배치 작업으로 주기적으로 집계하는 것이 효율적입니다. 매일 자정에 전날의 통계를 집계하여 별도의 통계 테이블에 저장합니다.

**SR-069: 로그 정리**
오래된 로그 데이터는 주기적으로 정리하여 스토리지 공간을 확보해야 합니다. 90일 이상 된 로그는 아카이브하거나 삭제합니다. 법적 요구사항이나 감사 목적으로 보관이 필요한 로그는 별도로 장기 보관합니다.

### 4.9 API 문서화

**SR-070: GraphQL 스키마 문서**
모든 GraphQL 쿼리, 뮤테이션, 구독은 스키마에 상세한 설명이 포함되어야 합니다. 각 필드의 의미, 필수 여부, 데이터 타입, 예시가 명시되어야 합니다.

**SR-071: GraphQL Playground**
개발 환경에서는 GraphQL Playground를 활성화하여 개발자가 API를 쉽게 테스트할 수 있도록 해야 합니다. Playground는 자동 완성, 스키마 탐색, 쿼리 실행 기능을 제공합니다. 프로덕션 환경에서는 보안을 위해 비활성화합니다.

**SR-072: API 버전 관리**
API는 버전을 관리하여 하위 호환성을 유지해야 합니다. 필드 추가는 하위 호환되지만, 필드 제거나 타입 변경은 새 버전을 만들어야 합니다. 구 버전 API는 일정 기간 유지한 후 deprecated 표시와 함께 종료합니다.

## 5. 블록체인 시스템 요구사항

### 5.1 블록체인 네트워크

**SR-073: Polygon 네트워크**
BlockPick 스마트 컨트랙트는 Polygon 블록체인에 배포되어야 합니다. Polygon은 이더리움의 레이어 2 솔루션으로, 빠른 트랜잭션 처리(약 2초)와 저렴한 가스비(수 센트)를 제공합니다. 초기 개발과 테스트는 Polygon Amoy Testnet에서 진행하고, 프로덕션은 Polygon Mainnet에 배포합니다.

**SR-074: Solidity 버전**
스마트 컨트랙트는 Solidity 버전 0.8.20 이상으로 작성되어야 합니다. Solidity 0.8.x는 오버플로우/언더플로우 보호가 내장되어 있어 보안성이 향상되었습니다.

**SR-075: ERC-20 토큰 호환성**
향후 플랫폼 토큰을 발행할 경우를 대비하여, ERC-20 표준을 지원할 수 있도록 설계되어야 합니다. 현재는 MATIC 토큰을 가스비로 사용하지만, 향후 자체 토큰 도입 가능성을 고려합니다.

### 5.2 스마트 컨트랙트 구조

**SR-076: GameManager 컨트랙트**
게임 생성, 참여, 종료를 관리하는 GameManager 스마트 컨트랙트가 있어야 합니다. 이 컨트랙트는 다음 기능을 포함합니다. 첫째, createGame 함수로 새로운 게임을 생성합니다. 둘째, participateGame 함수로 암호화된 좌표를 제출하고 게임에 참여합니다. 셋째, finalizeGame 함수로 게임을 종료하고 당첨자를 선정합니다. 넷째, claimPrize 함수로 당첨자가 상금을 청구합니다.

**SR-077: 암호화 키 관리**
게임 참여 시 사용자가 선택한 블록 좌표는 암호화되어 저장되어야 합니다. 암호화 키는 서버에서 생성되며, 게임 종료 전까지는 공개되지 않습니다. 게임 종료 후 암호화 키가 공개되면 모든 참여자의 좌표를 복호화할 수 있습니다. 이를 위해 별도의 EncryptionKey 매핑을 스마트 컨트랙트에 저장합니다.

**SR-078: 이벤트 발행**
스마트 컨트랙트는 주요 작업마다 이벤트를 발행해야 합니다. GameCreated, ParticipationRecorded, GameFinalized, PrizeClaimed 등의 이벤트를 정의하고, 각 이벤트에는 관련 데이터(게임 ID, 사용자 주소, 타임스탬프 등)가 포함됩니다. 서버와 클라이언트는 이러한 이벤트를 리스닝하여 상태를 동기화합니다.

**SR-079: 접근 제어**
특정 함수는 권한이 있는 주소만 호출할 수 있어야 합니다. OpenZeppelin의 Ownable 또는 AccessControl 컨트랙트를 상속하여 역할 기반 접근 제어를 구현합니다. 예를 들어, finalizeGame 함수는 관리자만 호출할 수 있습니다.

**SR-080: 업그레이드 가능성**
스마트 컨트랙트는 향후 버그 수정이나 기능 추가를 위해 업그레이드 가능하도록 설계되어야 합니다. OpenZeppelin의 프록시 패턴(예: UUPS 또는 Transparent Proxy)을 사용하여 컨트랙트 로직을 업그레이드할 수 있도록 합니다. 단, 업그레이드 권한은 다중 서명 지갑으로 관리하여 중앙화 위험을 최소화합니다.

### 5.3 Chainlink VRF 통합

**SR-081: 난수 생성**
공정한 당첨자 선정을 위해 Chainlink VRF(Verifiable Random Function)를 사용하여 검증 가능한 난수를 생성해야 합니다. Chainlink VRF는 블록체인 상에서 조작 불가능한 난수를 제공하며, 누구나 난수의 유효성을 검증할 수 있습니다.

**SR-082: VRF 구독**
Chainlink VRF를 사용하기 위해 구독(Subscription)을 생성하고 LINK 토큰으로 충전해야 합니다. 스마트 컨트랙트는 VRFConsumerBaseV2를 상속하며, requestRandomWords 함수를 호출하여 난수를 요청합니다.

**SR-083: 난수 콜백**
Chainlink VRF는 비동기적으로 난수를 반환합니다. 스마트 컨트랙트는 fulfillRandomWords 콜백 함수를 구현하여 난수를 수신하고, 이를 기반으로 당첨 블록을 선정합니다. 콜백 함수 내에서 당첨자를 결정하고 GameFinalized 이벤트를 발행합니다.

**SR-084: VRF 비용 관리**
Chainlink VRF 사용에는 LINK 토큰 비용이 발생합니다. 구독 잔액을 주기적으로 모니터링하여 잔액이 부족하면 자동으로 충전되도록 해야 합니다. 비용은 플랫폼 운영비에 포함되며, 게임 참가비로 충당됩니다.

### 5.4 가스 최적화

**SR-085: 효율적인 데이터 저장**
블록체인 스토리지 비용은 매우 비싸므로, 데이터를 효율적으로 저장해야 합니다. 불필요한 데이터는 저장하지 않으며, 가능한 경우 데이터를 압축하거나 해시값만 저장합니다. 예를 들어, 좌표 배열 대신 좌표의 해시를 저장할 수 있습니다.

**SR-086: 배치 처리**
여러 작업을 한 번의 트랜잭션으로 처리하여 가스비를 절약해야 합니다. 예를 들어, 여러 당첨자에게 상금을 분배할 때 각자 별도의 트랜잭션이 아닌 하나의 트랜잭션으로 일괄 처리합니다.

**SR-087: 변수 패킹**
Solidity의 스토리지 슬롯을 효율적으로 사용하기 위해 변수 패킹을 활용해야 합니다. uint256 대신 필요한 최소 크기의 타입(예: uint64, uint32)을 사용하고, 관련된 변수를 함께 선언하여 하나의 스토리지 슬롯에 저장되도록 합니다.

### 5.5 보안

**SR-088: 재진입 공격 방지**
스마트 컨트랙트는 재진입(reentrancy) 공격으로부터 보호되어야 합니다. OpenZeppelin의 ReentrancyGuard를 사용하거나, Checks-Effects-Interactions 패턴을 따라 상태 변경을 외부 호출 이전에 완료해야 합니다.

**SR-089: 정수 오버플로우/언더플로우 방지**
Solidity 0.8.x는 기본적으로 오버플로우/언더플로우를 검사하지만, 명시적으로 SafeMath를 사용하거나 unchecked 블록을 신중하게 사용해야 합니다.

**SR-090: 접근 제어 검증**
모든 중요한 함수는 호출자의 권한을 검증해야 합니다. onlyOwner, onlyRole 등의 modifier를 사용하여 권한이 없는 사용자의 접근을 차단합니다.

**SR-091: 감사(Audit)**
스마트 컨트랙트는 배포 전에 전문 보안 감사 기관의 감사를 받아야 합니다. 알려진 취약점(예: SWC Registry)을 검사하고, 감사 결과를 공개하여 투명성을 제공합니다.

## 6. 데이터베이스 요구사항

### 6.1 데이터베이스 시스템

**SR-092: PostgreSQL 사용**
주 데이터베이스는 PostgreSQL 버전 15 이상을 사용해야 합니다. PostgreSQL은 강력한 기능, 높은 안정성, ACID 트랜잭션 지원을 제공하는 오픈소스 관계형 데이터베이스입니다.

**SR-093: 스키마 설계**
데이터베이스 스키마는 정규화 원칙을 따라 설계되어야 합니다. 일반적으로 제3정규형(3NF)을 목표로 하며, 성능상 필요한 경우에만 비정규화를 고려합니다. 테이블 간 관계는 외래 키 제약조건으로 명확히 정의됩니다.

**SR-094: 인덱스 최적화**
자주 조회되는 컬럼에는 인덱스를 생성하여 쿼리 성능을 향상시켜야 합니다. 예를 들어, users 테이블의 email 컬럼, games 테이블의 status와 endTime 컬럼, participations 테이블의 userId와 gameId 컬럼에 인덱스를 생성합니다. 복합 인덱스도 필요에 따라 사용합니다.

**SR-095: 파티셔닝**
대량의 데이터를 효율적으로 관리하기 위해 테이블 파티셔닝을 사용할 수 있습니다. 예를 들어, participations 테이블은 참여 날짜를 기준으로 월별 파티션으로 나눌 수 있습니다. 이를 통해 오래된 데이터의 조회와 삭제가 빨라집니다.

### 6.2 주요 테이블

**SR-096: users 테이블**
사용자 정보를 저장하는 테이블입니다. 컬럼은 다음과 같습니다. id(기본키, UUID), email(문자열, 고유, 비null), passwordHash(문자열, 비null), nickname(문자열), walletAddress(문자열, 고유), createdAt(타임스탬프), updatedAt(타임스탬프), role(열거형: user, admin).

**SR-097: games 테이블**
게임 정보를 저장하는 테이블입니다. 컬럼은 다음과 같습니다. id(기본키, UUID), type(열거형: DAILY, SELECT, VIBE, PRIME), entryFee(정수, Event Cash), totalPrize(정수, Event Cash), status(열거형: ONGOING, CLOSED, FINALIZED), startTime(타임스탬프), endTime(타임스탬프), maxParticipants(정수), currentParticipants(정수), winningBlock(JSON, x와 y 좌표), contractAddress(문자열), encryptionKey(문자열), createdAt(타임스탬프), updatedAt(타임스탬프).

**SR-098: participations 테이블**
게임 참여 기록을 저장하는 테이블입니다. 컬럼은 다음과 같습니다. id(기본키, UUID), gameId(외래키, games.id 참조), userId(외래키, users.id 참조), selectedBlocks(JSON 배열, 9개의 좌표), encryptedCoordinates(문자열), transactionHash(문자열), isWinner(불리언), prizeAmount(정수), createdAt(타임스탬프).

**SR-099: transactions 테이블**
Event Cash 관련 거래 내역을 저장하는 테이블입니다. 컬럼은 다음과 같습니다. id(기본키, UUID), userId(외래키, users.id 참조), type(열거형: CHARGE, SPEND, WIN, WITHDRAW), amount(정수), balanceAfter(정수), description(문자열), paymentMethod(문자열), externalId(문자열, PG사 거래 ID), status(열거형: PENDING, COMPLETED, FAILED), createdAt(타임스탬프).

**SR-100: notifications 테이블**
알림 발송 기록을 저장하는 테이블입니다. 컬럼은 다음과 같습니다. id(기본키, UUID), userId(외래키, users.id 참조), type(열거형: GAME_END, WIN, CHARGE_COMPLETE, WITHDRAW_COMPLETE), title(문자열), body(문자열), data(JSON, 추가 데이터), sentAt(타임스탬프), isRead(불리언).

### 6.3 데이터 무결성

**SR-101: 외래 키 제약조건**
테이블 간 관계는 외래 키 제약조건으로 강제되어야 합니다. 예를 들어, participations 테이블의 gameId는 games 테이블의 id를 참조하며, 존재하지 않는 gameId는 삽입할 수 없습니다. 삭제 시에는 CASCADE, SET NULL, RESTRICT 등 적절한 옵션을 설정합니다.

**SR-102: 체크 제약조건**
데이터의 유효성을 보장하기 위해 체크 제약조건을 사용해야 합니다. 예를 들어, entryFee는 항상 0보다 커야 하며, currentParticipants는 maxParticipants를 초과할 수 없습니다.

**SR-103: 고유 제약조건**
고유해야 하는 컬럼에는 고유 제약조건을 설정해야 합니다. 예를 들어, users 테이블의 email과 walletAddress는 고유해야 하며, 중복된 값이 삽입되면 에러가 발생합니다.

**SR-104: NOT NULL 제약조건**
필수 컬럼에는 NOT NULL 제약조건을 설정하여 null 값이 저장되지 않도록 해야 합니다.

### 6.4 백업 및 복제

**SR-105: 자동 백업**
데이터베이스는 매일 자동으로 백업되어야 합니다. 전체 백업은 매일 새벽 3시에 실행되며, 증분 백업은 6시간마다 실행됩니다. 백업 파일은 별도의 스토리지(예: AWS S3)에 암호화되어 저장되며, 최소 30일간 보관됩니다.

**SR-106: 읽기 전용 복제본**
읽기 성능을 향상시키기 위해 읽기 전용 복제본(Read Replica)을 운영해야 합니다. 주 데이터베이스는 쓰기 작업을 처리하고, 복제본은 읽기 작업을 처리합니다. Prisma에서는 연결 문자열을 구분하여 쿼리 타입에 따라 적절한 데이터베이스로 라우팅합니다.

**SR-107: 장애 복구**
주 데이터베이스 장애 시 자동으로 복제본이 승격(promotion)되어 서비스 중단을 최소화해야 합니다. AWS RDS의 Multi-AZ 배포를 사용하면 자동 장애 조치(failover)가 지원됩니다.

### 6.5 성능 모니터링

**SR-108: 슬로우 쿼리 로깅**
실행 시간이 오래 걸리는 쿼리(예: 1초 이상)는 로그에 기록되어야 합니다. 슬로우 쿼리 로그를 분석하여 성능 병목 지점을 파악하고, 인덱스 추가나 쿼리 최적화를 수행합니다.

**SR-109: 연결 풀 모니터링**
데이터베이스 연결 풀의 상태를 모니터링하여 연결 부족이나 과도한 대기 시간이 발생하지 않도록 해야 합니다. 연결 수, 대기 중인 요청 수, 평균 대기 시간 등의 메트릭을 수집합니다.

**SR-110: 디스크 및 메모리 모니터링**
데이터베이스 서버의 디스크 사용량, 메모리 사용량, CPU 사용률을 지속적으로 모니터링해야 합니다. 임계값을 초과하면 알림을 발송하고, 필요시 리소스를 확장합니다.

## 7. 인프라 요구사항

### 7.1 클라우드 플랫폼

**SR-111: AWS 사용**
BlockPick의 모든 인프라는 Amazon Web Services(AWS)에서 운영되어야 합니다. AWS는 높은 가용성, 확장성, 보안, 다양한 관리 도구를 제공하는 클라우드 플랫폼입니다.

**SR-112: 리전 선택**
서비스는 주로 한국 사용자를 대상으로 하므로, AWS 서울 리전(ap-northeast-2)을 기본 리전으로 사용해야 합니다. 재해 복구를 위해 도쿄 리전(ap-northeast-1)을 보조 리전으로 설정할 수 있습니다.

**SR-113: 가용 영역**
고가용성을 위해 최소 2개의 가용 영역(Availability Zone)을 사용해야 합니다. 서버, 데이터베이스, 로드 밸런서 등은 여러 가용 영역에 분산 배치되어 하나의 가용 영역 장애 시에도 서비스가 계속됩니다.

### 7.2 컴퓨팅 리소스

**SR-114: EC2 또는 ECS**
백엔드 서버는 EC2 인스턴스 또는 ECS(Elastic Container Service) 컨테이너로 실행되어야 합니다. 초기에는 관리가 간단한 EC2를 사용할 수 있지만, 향후 확장성과 유연성을 위해 ECS로 전환을 고려합니다.

**SR-115: Auto Scaling**
트래픽 변화에 따라 서버 인스턴스 수를 자동으로 조절하는 Auto Scaling을 구현해야 합니다. CPU 사용률이 70% 이상일 때 인스턴스를 추가하고, 30% 이하일 때 축소합니다. 최소 인스턴스 수는 2개, 최대는 10개로 설정합니다.

**SR-116: 로드 밸런서**
사용자 요청은 Application Load Balancer(ALB)를 통해 여러 서버 인스턴스에 분산되어야 합니다. ALB는 HTTPS 종료, 헬스 체크, 경로 기반 라우팅 등의 기능을 제공합니다.

### 7.3 데이터베이스 인프라

**SR-117: RDS 사용**
PostgreSQL 데이터베이스는 AWS RDS(Relational Database Service)를 사용하여 관리되어야 합니다. RDS는 자동 백업, 패치, 모니터링, 장애 조치 등의 관리 작업을 자동화합니다.

**SR-118: 인스턴스 타입**
초기에는 db.t3.medium 인스턴스 타입을 사용하고, 트래픽 증가에 따라 db.r5.large 이상으로 확장합니다. 프로덕션 환경에서는 Multi-AZ 배포를 사용하여 고가용성을 보장합니다.

**SR-119: 스토리지**
데이터베이스 스토리지는 SSD 기반의 gp3 타입을 사용해야 합니다. 초기 용량은 100GB로 시작하며, 자동 확장(Auto Scaling Storage)을 활성화하여 용량이 부족하면 자동으로 증가합니다.

### 7.4 캐시 인프라

**SR-120: ElastiCache for Redis**
Redis 캐시는 AWS ElastiCache for Redis를 사용하여 관리되어야 합니다. ElastiCache는 Redis의 설치, 패치, 백업, 모니터링을 자동화하며, 고가용성을 제공합니다.

**SR-121: 클러스터 모드**
확장성을 위해 Redis 클러스터 모드를 사용할 수 있습니다. 클러스터 모드는 데이터를 여러 노드에 분산하여 저장하고, 읽기/쓰기 성능을 향상시킵니다. 초기에는 단일 노드로 시작하고, 필요시 클러스터로 전환합니다.

**SR-122: 백업 및 복제**
Redis 데이터는 주기적으로 스냅샷을 생성하여 백업되어야 합니다. 또한 읽기 복제본을 생성하여 읽기 성능을 향상시키고, 장애 시 복제본을 승격할 수 있습니다.

### 7.5 스토리지

**SR-123: S3 사용**
파일 저장(예: 사용자 프로필 이미지, 백업 파일, 로그)은 AWS S3를 사용해야 합니다. S3는 높은 내구성(99.999999999%), 가용성, 확장성을 제공합니다.

**SR-124: 버킷 정책**
S3 버킷은 최소 권한 원칙에 따라 접근 권한을 설정해야 합니다. 공개 접근이 필요한 파일(예: 프로필 이미지)과 비공개 파일(예: 백업)을 별도의 버킷에 저장하며, 버킷 정책과 IAM 역할로 접근을 제어합니다.

**SR-125: 라이프사이클 정책**
오래된 파일은 자동으로 삭제하거나 저렴한 스토리지 클래스(예: Glacier)로 이동하는 라이프사이클 정책을 설정해야 합니다. 예를 들어, 백업 파일은 30일 후 Glacier로 이동하고, 90일 후 삭제합니다.

### 7.6 네트워킹

**SR-126: VPC 구성**
모든 리소스는 Virtual Private Cloud(VPC) 내에 배치되어야 합니다. VPC는 격리된 네트워크 환경을 제공하며, 서브넷, 라우팅 테이블, 보안 그룹 등을 통해 네트워크를 세밀하게 제어할 수 있습니다.

**SR-127: 퍼블릭 및 프라이빗 서브넷**
웹 서버와 로드 밸런서는 퍼블릭 서브넷에, 데이터베이스와 캐시는 프라이빗 서브넷에 배치해야 합니다. 프라이빗 서브넷의 리소스는 인터넷에서 직접 접근할 수 없으며, NAT 게이트웨이를 통해서만 외부 통신이 가능합니다.

**SR-128: 보안 그룹**
각 리소스는 필요한 포트만 열도록 보안 그룹을 설정해야 합니다. 예를 들어, 웹 서버는 80(HTTP)과 443(HTTPS) 포트만 열고, 데이터베이스는 5432(PostgreSQL) 포트를 웹 서버 보안 그룹에서만 접근 가능하도록 설정합니다.

**SR-129: WAF(Web Application Firewall)**
DDoS 공격, SQL 인젝션, XSS 등 웹 공격으로부터 보호하기 위해 AWS WAF를 설정해야 합니다. WAF 규칙을 정의하여 악의적인 요청을 차단하고, 정상 트래픽만 서버로 전달합니다.

### 7.7 CDN

**SR-130: CloudFront 사용**
정적 컨텐츠(이미지, CSS, JavaScript)는 AWS CloudFront CDN을 통해 제공되어야 합니다. CloudFront는 전 세계에 분산된 엣지 로케이션에서 컨텐츠를 캐싱하여 빠른 로딩 속도를 제공합니다.

**SR-131: 캐시 정책**
CloudFront는 적절한 캐시 정책을 설정하여 효율성을 극대화해야 합니다. 자주 변경되지 않는 리소스(예: 로고)는 긴 TTL(예: 30일)을, 자주 변경되는 리소스(예: API 응답)는 짧은 TTL(예: 5분)을 설정합니다.

**SR-132: HTTPS 사용**
CloudFront는 HTTPS를 사용하여 컨텐츠를 제공해야 합니다. SSL/TLS 인증서는 AWS Certificate Manager(ACM)에서 무료로 발급받을 수 있습니다.

## 8. 보안 요구사항

### 8.1 데이터 암호화

**SR-133: 전송 중 암호화**
모든 데이터 전송은 TLS 1.2 이상을 사용하여 암호화되어야 합니다. 클라이언트와 서버 간 통신, 서버와 데이터베이스 간 통신, 서버와 블록체인 간 통신 모두 암호화됩니다.

**SR-134: 저장 시 암호화**
민감한 데이터(비밀번호, 개인키, 계좌 정보 등)는 저장 시 암호화되어야 합니다. 비밀번호는 bcrypt로 해싱하여 저장하며, 개인키는 AES-256-CBC로 암호화하여 저장합니다. 데이터베이스 볼륨과 백업 파일도 AWS KMS를 사용하여 암호화됩니다.

**SR-135: 암호화 키 관리**
암호화 키는 AWS Secrets Manager 또는 KMS(Key Management Service)를 사용하여 안전하게 관리되어야 합니다. 키는 절대로 코드에 하드코딩되지 않으며, 환경 변수나 시크릿 스토어에서 로드됩니다. 키는 정기적으로 로테이션됩니다.

### 8.2 인증 및 접근 제어

**SR-136: 강력한 비밀번호 정책**
사용자 비밀번호는 최소 8자 이상이어야 하며, 대문자, 소문자, 숫자, 특수문자 중 최소 3가지를 포함해야 합니다. 일반적인 비밀번호(예: password123)는 거부됩니다.

**SR-137: 다단계 인증(MFA)**
향후 고액 출금이나 중요한 작업 시 다단계 인증을 도입할 수 있습니다. SMS, 이메일, TOTP 앱 등을 통해 추가 인증을 요구합니다.

**SR-138: IAM 역할 및 정책**
AWS 리소스 접근은 IAM(Identity and Access Management) 역할과 정책을 사용하여 제어되어야 합니다. 최소 권한 원칙에 따라 각 역할은 필요한 최소한의 권한만 부여받습니다. 루트 계정은 절대 일상적인 작업에 사용하지 않습니다.

**SR-139: API 키 보안**
외부 서비스(PG사, FCM, Chainlink 등)의 API 키는 코드에 포함되지 않으며, 환경 변수 또는 AWS Secrets Manager에 저장되어야 합니다. API 키는 정기적으로 교체됩니다.

### 8.3 입력 검증 및 위생 처리

**SR-140: 입력 검증**
모든 사용자 입력은 서버 측에서 검증되어야 합니다. 클라이언트 측 검증은 사용자 경험을 위한 것일 뿐, 보안을 보장하지 못합니다. 데이터 타입, 길이, 형식, 범위 등을 검증하고, 유효하지 않은 입력은 거부합니다.

**SR-141: SQL 인젝션 방지**
SQL 쿼리는 절대로 문자열 연결로 생성하지 않으며, 파라미터화된 쿼리 또는 ORM(Prisma)을 사용해야 합니다. 이를 통해 SQL 인젝션 공격을 방지합니다.

**SR-142: XSS 방지**
사용자가 입력한 데이터를 HTML에 표시할 때는 적절히 이스케이프하여 XSS(Cross-Site Scripting) 공격을 방지해야 합니다. React와 Flutter는 기본적으로 XSS 방지 기능을 제공하지만, dangerouslySetInnerHTML 같은 위험한 API는 사용하지 않습니다.

**SR-143: CSRF 방지**
상태를 변경하는 API(POST, PUT, DELETE)는 CSRF(Cross-Site Request Forgery) 토큰을 사용하여 보호되어야 합니다. GraphQL 뮤테이션은 JWT 토큰 자체가 CSRF 방지 역할을 하지만, 추가로 SameSite 쿠키 속성을 설정할 수 있습니다.

### 8.4 로깅 및 모니터링

**SR-144: 보안 이벤트 로깅**
로그인 실패, 권한 없는 접근 시도, 데이터 변경 등 보안 관련 이벤트는 모두 로깅되어야 합니다. 로그에는 타임스탬프, 사용자 ID, IP 주소, 액션 등이 포함됩니다.

**SR-145: 로그 보호**
로그 파일은 무단 변경이나 삭제로부터 보호되어야 합니다. 로그는 별도의 스토리지에 저장되며, 쓰기 전용 권한만 부여됩니다. 중요한 로그는 외부 로깅 서비스(예: AWS CloudWatch Logs)로 전송하여 안전하게 보관합니다.

**SR-146: 이상 탐지**
비정상적인 활동(예: 단시간 내 대량의 로그인 시도, 비정상적인 트래픽 패턴)을 자동으로 탐지하고 알림을 발송하는 시스템을 구축해야 합니다. AWS GuardDuty 같은 서비스를 활용할 수 있습니다.

### 8.5 개인정보 보호

**SR-147: 개인정보 최소 수집**
서비스 제공에 필요한 최소한의 개인정보만 수집해야 합니다. 불필요한 정보는 요청하지 않으며, 사용자에게 수집 목적을 명확히 고지합니다.

**SR-148: 개인정보 접근 제어**
개인정보에 접근할 수 있는 직원은 최소한으로 제한하며, 접근 기록을 남겨야 합니다. 개인정보 처리 시스템은 별도의 네트워크에 격리되며, VPN을 통해서만 접근 가능합니다.

**SR-149: 개인정보 파기**
사용자가 계정을 삭제하거나 개인정보 보유 기간이 만료되면, 개인정보는 즉시 파기되어야 합니다. 데이터베이스에서 삭제하고, 백업에서도 제거합니다. 법적 보관 의무가 있는 정보는 별도로 분리하여 보관합니다.

## 9. 성능 요구사항

### 9.1 응답 시간

**SR-150: API 응답 시간**
모든 API 요청은 95 백분위수 기준 500ms 이하의 응답 시간을 가져야 합니다. 간단한 조회는 100ms 이내, 복잡한 쿼리는 500ms 이내에 완료되어야 합니다. 응답 시간이 1초를 초과하면 경고 알림을 발송합니다.

**SR-151: 데이터베이스 쿼리 시간**
데이터베이스 쿼리는 평균 50ms 이하로 실행되어야 합니다. 인덱스를 적절히 사용하고, N+1 쿼리 문제를 피하며, 필요시 쿼리를 최적화합니다.

**SR-152: 블록체인 트랜잭션 시간**
블록체인 트랜잭션은 평균 10-20초 내에 확인되어야 합니다. Polygon 네트워크의 블록 시간은 약 2초이며, 안전을 위해 5-10개의 블록 확인을 기다립니다.

### 9.2 처리량

**SR-153: 동시 사용자**
시스템은 최소 10,000명의 동시 사용자를 지원해야 합니다. 각 사용자는 평균 분당 5개의 요청을 보내므로, 시스템은 초당 약 830개의 요청을 처리할 수 있어야 합니다.

**SR-154: 게임 참가 처리**
피크 시간(예: 게임 종료 직전)에는 초당 100개의 게임 참가 요청을 처리할 수 있어야 합니다. 큐잉 시스템을 사용하여 요청을 순차적으로 처리하고, 사용자에게 대기 시간을 안내합니다.

**SR-155: 알림 발송**
대량의 푸시 알림(예: 게임 종료 알림)을 발송할 때, 분당 10,000개 이상의 알림을 발송할 수 있어야 합니다. FCM의 배치 발송 API를 사용하여 효율성을 높입니다.

### 9.3 렌더링 성능

**SR-156: 그리드 렌더링 프레임률**
게임 화면의 그리드는 60fps를 유지해야 합니다. 프레임 드롭이 발생하면 사용자 경험이 저하되므로, LOD 시스템, 오프스크린 캔버스, 렌더링 최적화 등의 기법을 사용합니다.

**SR-157: 앱 초기 로딩**
애플리케이션은 실행 후 3초 이내에 메인 화면을 표시해야 합니다. 필요한 리소스만 먼저 로드하고, 나머지는 백그라운드에서 지연 로딩합니다.

**SR-158: 화면 전환**
화면 전환 애니메이션은 부드럽게 실행되어야 하며, 60fps를 유지해야 합니다. 무거운 작업은 애니메이션이 완료된 후 실행합니다.

## 10. 확장성 요구사항

### 10.1 수평 확장

**SR-159: 스테이트리스 서버**
백엔드 서버는 스테이트리스(stateless)로 설계되어야 합니다. 세션 정보는 서버 메모리가 아닌 Redis에 저장되며, 어느 서버 인스턴스로 요청이 가더라도 동일한 결과를 반환합니다. 이를 통해 서버 인스턴스를 자유롭게 추가하거나 제거할 수 있습니다.

**SR-160: 로드 밸런싱**
로드 밸런서는 요청을 여러 서버 인스턴스에 균등하게 분산해야 합니다. 라운드 로빈, 최소 연결, IP 해시 등의 알고리즘을 사용할 수 있으며, 헬스 체크를 통해 비정상 인스턴스는 제외합니다.

**SR-161: 데이터베이스 샤딩**
사용자 수가 크게 증가하면 데이터베이스를 샤딩하여 데이터를 여러 데이터베이스에 분산 저장할 수 있어야 합니다. 예를 들어, 사용자 ID의 해시값을 기준으로 데이터를 여러 샤드로 나눕니다.

### 10.2 수직 확장

**SR-162: 인스턴스 크기 조정**
트래픽 증가에 따라 서버와 데이터베이스 인스턴스의 크기를 확장할 수 있어야 합니다. AWS에서는 인스턴스 타입을 변경하여 CPU, 메모리, 네트워크 성능을 향상시킬 수 있습니다. 다운타임을 최소화하기 위해 블루-그린 배포나 롤링 업데이트를 사용합니다.

### 10.3 캐싱 전략

**SR-163: 다층 캐싱**
성능을 극대화하기 위해 다층 캐싱 전략을 사용해야 합니다. 첫 번째 계층은 애플리케이션 메모리 캐시(예: Riverpod 상태), 두 번째 계층은 Redis 캐시, 세 번째 계층은 데이터베이스입니다. 요청은 상위 계층부터 확인하고, 캐시 미스 시에만 하위 계층으로 내려갑니다.

**SR-164: CDN 활용**
정적 컨텐츠는 CDN에 캐싱하여 서버 부하를 줄이고 전 세계 사용자에게 빠른 컨텐츠 제공을 해야 합니다.

## 11. 모니터링 및 로깅 요구사항

### 11.1 시스템 모니터링

**SR-165: CloudWatch 사용**
모든 AWS 리소스의 메트릭은 CloudWatch를 통해 수집되어야 합니다. CPU 사용률, 메모리 사용률, 디스크 I/O, 네트워크 트래픽 등을 실시간으로 모니터링합니다.

**SR-166: 커스텀 메트릭**
애플리케이션 수준의 메트릭(예: API 요청 수, 에러율, 응답 시간)도 수집되어야 합니다. 이러한 커스텀 메트릭은 CloudWatch에 전송되거나, Prometheus + Grafana 같은 모니터링 스택을 사용할 수 있습니다.

**SR-167: 알림 설정**
중요한 메트릭이 임계값을 초과하면 즉시 알림을 발송해야 합니다. 예를 들어, CPU 사용률이 80% 이상, 에러율이 5% 이상, 응답 시간이 1초 이상일 때 Slack이나 이메일로 알림을 보냅니다.

**SR-168: 대시보드**
주요 메트릭을 한눈에 볼 수 있는 대시보드를 구축해야 합니다. CloudWatch Dashboard나 Grafana를 사용하여 실시간 차트와 그래프를 표시합니다.

### 11.2 애플리케이션 로깅

**SR-169: 구조화된 로그**
로그는 구조화된 형식(JSON)으로 출력되어야 합니다. 각 로그 항목에는 타임스탬프, 로그 레벨, 메시지, 컨텍스트(사용자 ID, 요청 ID 등), 스택 트레이스(에러 시)가 포함됩니다.

**SR-170: 로그 집중화**
모든 서버 인스턴스의 로그는 중앙 로깅 시스템(예: CloudWatch Logs, ELK Stack)으로 전송되어야 합니다. 이를 통해 여러 서버의 로그를 한 곳에서 검색하고 분석할 수 있습니다.

**SR-171: 로그 보존**
로그는 적절한 기간 동안 보존되어야 합니다. 최근 30일의 로그는 빠른 검색을 위해 온라인 스토리지에 보관하고, 31-90일의 로그는 아카이브 스토리지에, 90일 이상의 로그는 삭제하거나 콜드 스토리지에 보관합니다.

### 11.3 분산 추적

**SR-172: 요청 ID 부여**
모든 API 요청에 고유한 요청 ID를 부여하여, 요청이 여러 서비스와 데이터베이스를 거치는 동안 추적할 수 있어야 합니다. 요청 ID는 모든 로그와 메트릭에 포함됩니다.

**SR-173: 분산 추적 시스템**
마이크로서비스 환경에서는 AWS X-Ray나 Jaeger 같은 분산 추적 시스템을 사용하여 요청의 전체 경로를 시각화해야 합니다. 이를 통해 병목 지점을 파악하고 성능을 최적화합니다.

## 12. 백업 및 복구 요구사항

### 12.1 데이터베이스 백업

**SR-174: 자동 백업**
RDS는 매일 자동 백업을 수행하며, 백업 보존 기간은 최소 7일입니다. 전체 백업 외에도 트랜잭션 로그를 지속적으로 백업하여 특정 시점으로 복구(Point-in-Time Recovery)할 수 있습니다.

**SR-175: 수동 스냅샷**
중요한 변경(예: 대규모 마이그레이션) 전에는 수동으로 스냅샷을 생성하여 안전망을 확보해야 합니다.

### 12.2 재해 복구

**SR-176: RTO 및 RPO**
재해 복구 목표를 명확히 정의해야 합니다. RTO(Recovery Time Objective, 복구 목표 시간)는 4시간 이내, RPO(Recovery Point Objective, 복구 목표 시점)는 1시간 이내로 설정합니다. 즉, 장애 발생 시 4시간 내에 서비스를 복구하고, 최대 1시간의 데이터 손실을 감수합니다.

**SR-177: 백업 리전**
백업 데이터는 주 리전과 다른 리전에도 복제되어야 합니다. 주 리전이 완전히 손상되더라도 백업 리전의 데이터로 서비스를 복구할 수 있습니다.

**SR-178: 복구 테스트**
재해 복구 계획은 정기적으로 테스트되어야 합니다. 최소 분기에 한 번씩 백업으로부터 데이터를 복원하는 훈련을 실시하여, 실제 재해 시 신속하게 대응할 수 있도록 합니다.

## 13. 외부 시스템 연동 요구사항

### 13.1 PG사 연동

**SR-179: 표준 프로토콜**
PG사와의 연동은 REST API 또는 웹훅을 사용하며, 표준 프로토콜(HTTPS, JSON)을 따라야 합니다.

**SR-180: 에러 처리**
PG사 API 호출 실패 시 적절한 에러 처리와 재시도 로직을 구현해야 합니다. 일시적인 네트워크 오류는 재시도하고, 영구적인 오류는 로깅하고 관리자에게 알림을 보냅니다.

### 13.2 FCM 연동

**SR-181: Firebase Admin SDK**
Firebase Admin SDK를 사용하여 서버에서 FCM으로 푸시 알림을 발송합니다. SDK는 인증, 배치 발송, 에러 처리 등을 자동으로 처리합니다.

### 13.3 블록체인 노드 프로바이더

**SR-182: 다중 프로바이더**
Infura, Alchemy, QuickNode 등 여러 노드 프로바이더를 설정하여 가용성을 높여야 합니다. 주 프로바이더 실패 시 자동으로 백업 프로바이더로 전환됩니다.

**SR-183: 요청 제한 관리**
노드 프로바이더는 무료 티어에서 일일 요청 제한이 있습니다. 요청 수를 모니터링하고, 제한에 근접하면 유료 플랜으로 업그레이드하거나 여러 계정을 사용하여 분산합니다.
