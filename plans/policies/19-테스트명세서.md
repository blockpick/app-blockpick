## 1. 문서 개요

### 1.1 목적

본 테스트 명세서는 BlockPick 플랫폼의 품질을 보증하기 위한 포괄적인 테스트 계획 및 케이스를 정의합니다. 모든 기능이 요구사항을 만족하고, 안정적이며, 사용자 경험이 우수함을 검증하는 것을 목표로 합니다.

### 1.2 범위

본 문서는 다음을 포함합니다:

- **단위 테스트**: 개별 함수 및 모듈 테스트
- **통합 테스트**: 컴포넌트 간 상호작용 테스트
- **시스템 테스트**: 전체 시스템의 End-to-End 테스트
- **보안 테스트**: 취약점 및 보안 위협 테스트
- **성능 테스트**: 부하, 스트레스, 확장성 테스트
- **사용자 시나리오 테스트**: 실제 사용 시나리오 기반 테스트
- **블록체인 테스트**: 스마트 컨트랙트 및 블록체인 연동 테스트
- **모바일 앱 테스트**: Flutter 앱 (iOS/Android) 테스트

### 1.3 대상 독자

- **QA 엔지니어**: 테스트 케이스를 실행하고 결함을 보고
- **개발자**: 단위 테스트 작성 및 결함 수정
- **프로젝트 매니저**: 테스트 진행 상황 모니터링
- **DevOps**: 테스트 환경 구축 및 CI/CD 파이프라인 구성

### 1.4 용어 정의

**테스트 케이스(Test Case)**: 특정 기능이나 시나리오를 검증하기 위한 입력, 실행 조건, 예상 결과의 집합

**결함(Defect/Bug)**: 예상된 동작과 실제 동작 간의 차이

**회귀 테스트(Regression Test)**: 코드 변경 후 기존 기능이 정상 작동하는지 확인하는 테스트

**커버리지(Coverage)**: 테스트가 코드의 얼마나 많은 부분을 실행했는지를 나타내는 지표

**CI/CD**: Continuous Integration/Continuous Deployment, 지속적 통합 및 배포

## 2. 테스트 전략

### 2.1 테스트 접근 방법

BlockPick은 다층 테스트 전략을 채택합니다:

**피라미드 구조**: 단위 테스트(70%) > 통합 테스트(20%) > UI/E2E 테스트(10%)의 비율로 테스트를 구성하여 효율성과 안정성을 동시에 확보합니다.

**Shift-Left Testing**: 개발 초기 단계부터 테스트를 시작하여 결함을 조기에 발견하고 수정 비용을 최소화합니다.

**Risk-Based Testing**: 비즈니스 영향도가 높고 변경 빈도가 높은 기능에 테스트 리소스를 우선 배분합니다.

**Continuous Testing**: CI/CD 파이프라인에 자동화된 테스트를 통합하여 매 커밋마다 테스트를 실행합니다.

### 2.2 테스트 레벨

**단위 테스트 (Unit Test)**
- 개별 함수, 메서드, 컴포넌트를 독립적으로 테스트
- 개발자가 작성하고 실행
- Jest (백엔드), Flutter Test (앱) 사용
- 코드 커버리지 목표: 80% 이상

**통합 테스트 (Integration Test)**
- 여러 컴포넌트 간의 상호작용 테스트
- API 엔드포인트, 데이터베이스 연동, 외부 서비스 연동 테스트
- Supertest, Integration Test Runner 사용

**시스템 테스트 (System Test)**
- 전체 시스템의 End-to-End 기능 테스트
- 사용자 관점에서 전체 워크플로우 검증
- Playwright, Appium 사용

**인수 테스트 (Acceptance Test)**
- 비즈니스 요구사항 충족 여부 검증
- 사용자 스토리 기반 테스트
- 내부 팀 및 베타 사용자가 실행

### 2.3 테스트 유형

**기능 테스트 (Functional Test)**: 각 기능이 명세대로 동작하는지 검증

**비기능 테스트 (Non-Functional Test)**:
- 성능: 응답 시간, 처리량
- 보안: 취약점, 인증/인가
- 사용성: UI/UX, 접근성
- 호환성: 다양한 기기 및 OS

**회귀 테스트 (Regression Test)**: 기존 기능이 새로운 변경으로 인해 영향받지 않았는지 확인

**탐색적 테스트 (Exploratory Test)**: 스크립트 없이 자유롭게 탐색하며 예상치 못한 결함 발견

## 3. 테스트 범위 및 우선순위

### 3.1 테스트 범위

BlockPick의 모든 주요 기능 영역을 테스트합니다:

| 영역 | 포함 항목 | 우선순위 |
|------|-----------|----------|
| **인증 및 회원관리** | 회원가입, 로그인, 비밀번호 재설정, 프로필 관리 | 높음 |
| **게임 참여** | DAILY/SELECT/VIBE/PRIME 게임 참여, 블록 선택, 당첨 처리 | 최고 |
| **Event Cash** | 충전, 사용, 출금, 거래 내역 | 최고 |
| **Shopping Cash** | 충전, 상품 구매 시 사용, 환불 처리 | 높음 |
| **쇼핑몰** | 상품 조회, 구매, 결제, 배송 추적 | 높음 |
| **정산 시스템** | 파트너사 정산, 취소수수료 처리 | 높음 |
| **블록체인 연동** | 게임 참여 기록, 좌표 암호화, 당첨 검증 | 최고 |
| **알림** | 푸시 알림, 이메일, 인앱 알림 | 중간 |
| **관리자 기능** | 게임 생성, 사용자 관리, 통계 조회 | 중간 |
| **결제 시스템** | PG 연동, 카드 결제, 계좌이체 | 최고 |

### 3.2 우선순위 기준

**최고 (Critical)**: 핵심 비즈니스 기능, 금융 거래, 보안
- 게임 참여 및 당첨 처리
- Event Cash 및 Shopping Cash 시스템
- 결제 및 정산
- 블록체인 연동
- 인증 및 보안

**높음 (High)**: 주요 기능, 사용자 경험에 직접적 영향
- 상품 조회 및 구매
- 회원 관리
- 환불 처리

**중간 (Medium)**: 보조 기능, 운영 편의성
- 알림
- 관리자 기능
- 통계 및 리포트

**낮음 (Low)**: 부가 기능, 향후 개선 예정
- 소셜 기능
- 개인화 추천

### 3.3 테스트 제외 항목

다음 항목은 현재 범위에서 제외합니다:
- 아직 개발되지 않은 미래 기능
- 서드파티 라이브러리의 내부 로직 (단, 통합은 테스트)
- 외부 PG사의 내부 시스템 (단, API 연동은 테스트)

## 4. 테스트 환경

### 4.1 환경 구성

BlockPick은 다음 세 가지 환경을 운영합니다:

**개발 환경 (Development)**
- 용도: 개발자의 로컬 개발 및 초기 테스트
- 데이터: 샘플 데이터
- 블록체인: Polygon Mumbai Testnet
- URL: localhost:3000 (백엔드), localhost:8080 (프론트엔드)

**스테이징 환경 (Staging)**
- 용도: QA 테스트, 통합 테스트, UAT
- 데이터: 프로덕션과 유사한 테스트 데이터
- 블록체인: Polygon Mumbai Testnet
- URL: staging.blockpick.io
- 특징: 프로덕션 환경과 동일한 구성

**프로덕션 환경 (Production)**
- 용도: 실제 서비스
- 데이터: 실제 사용자 데이터
- 블록체인: Polygon Mainnet
- URL: blockpick.io
- 특징: 모니터링 및 알림 설정

### 4.2 테스트 데이터

**사용자 계정**:
- 테스트용 사용자 계정 (test_user_001@blockpick.io ~ test_user_100@blockpick.io)
- 다양한 역할: 일반 사용자, VIP 사용자, 관리자
- 다양한 상태: 신규, 활성, 휴면, 정지

**게임 데이터**:
- 진행 중인 게임 (각 타입별 5개씩)
- 종료된 게임 (히스토리 테스트용)
- 다양한 상태의 게임 (시작 전, 진행 중, 종료)

**캐시 데이터**:
- 다양한 잔액의 테스트 계정
- 충전/사용 히스토리

**상품 데이터**:
- 다양한 카테고리의 테스트 상품
- 다양한 가격대 (1만원 ~ 500만원)

### 4.3 테스트 도구

**백엔드 테스트**:
- Jest: 단위 및 통합 테스트
- Supertest: API 테스트
- Artillery: 부하 테스트

**프론트엔드/앱 테스트**:
- Flutter Test: 위젯 단위 테스트
- Integration Test: 통합 테스트
- Maestro: UI 자동화 테스트

**E2E 테스트**:
- Playwright: 웹 E2E 테스트
- Appium: 모바일 앱 E2E 테스트

**블록체인 테스트**:
- Hardhat: 스마트 컨트랙트 테스트
- Polygon Mumbai Testnet: 통합 테스트

**기타**:
- SonarQube: 코드 품질 분석
- OWASP ZAP: 보안 취약점 스캔
- Postman: API 수동 테스트

## 5. 단위 테스트

### 5.1 단위 테스트 원칙

**AAA 패턴**: Arrange(준비) - Act(실행) - Assert(검증) 패턴을 따릅니다.

**독립성**: 각 테스트는 독립적이어야 하며, 실행 순서에 영향받지 않아야 합니다.

**반복 가능성**: 동일한 입력에 대해 항상 동일한 결과를 반환해야 합니다.

**빠른 실행**: 단위 테스트는 밀리초 단위로 빠르게 실행되어야 합니다.

### 5.2 백엔드 단위 테스트

**테스트 대상**:
- GraphQL Resolvers
- 비즈니스 로직 함수
- 유틸리티 함수
- 데이터 검증 로직

**예시: 사용자 회원가입 로직 테스트**

```
TC-UNIT-AUTH-001: 유효한 입력으로 회원가입 성공
- 입력: 유효한 이메일, 비밀번호, 이름
- 예상 결과: 사용자 생성 성공, 비밀번호 해싱 확인, Event Cash 1,000원 지급

TC-UNIT-AUTH-002: 중복 이메일로 회원가입 실패
- 입력: 이미 존재하는 이메일
- 예상 결과: "이미 사용 중인 이메일입니다" 오류

TC-UNIT-AUTH-003: 약한 비밀번호로 회원가입 실패
- 입력: 7자 이하 비밀번호
- 예상 결과: "비밀번호는 최소 8자 이상" 오류

TC-UNIT-AUTH-004: 잘못된 이메일 형식으로 회원가입 실패
- 입력: "invalid-email"
- 예상 결과: "유효한 이메일 형식이 아닙니다" 오류
```

**예시: Event Cash 계산 로직 테스트**

```
TC-UNIT-CASH-001: Event Cash 충전 금액 정확성
- 입력: 충전 금액 10,000원
- 예상 결과: 잔액 10,000 캐시 증가

TC-UNIT-CASH-002: 게임 참가비 차감 정확성
- 입력: 참가비 1,000 캐시, 현재 잔액 10,000 캐시
- 예상 결과: 잔액 9,000 캐시

TC-UNIT-CASH-003: 잔액 부족 시 게임 참여 불가
- 입력: 참가비 1,000 캐시, 현재 잔액 500 캐시
- 예상 결과: "Event Cash가 부족합니다" 오류

TC-UNIT-CASH-004: 출금 수수료 계산 정확성
- 입력: 출금 금액 100,000 캐시
- 예상 결과: 수수료 5,000원 (5%), 실제 입금액 95,000원
```

### 5.3 프론트엔드 단위 테스트

**테스트 대상**:
- Flutter Widget
- 상태 관리 로직 (Provider, Riverpod)
- 데이터 모델 변환
- 유틸리티 함수

**예시: Widget 테스트**

```
TC-UNIT-WIDGET-001: GameCard 위젯이 게임 정보를 올바르게 표시
- 입력: 게임 데이터 (제목, 상금, 참여자 수)
- 예상 결과: 모든 정보가 화면에 표시됨

TC-UNIT-WIDGET-002: CashBalanceDisplay가 잔액을 올바르게 포맷
- 입력: 잔액 1234567 캐시
- 예상 결과: "1,234,567 캐시" 표시

TC-UNIT-WIDGET-003: 로딩 상태에서 로딩 인디케이터 표시
- 입력: isLoading = true
- 예상 결과: CircularProgressIndicator 표시
```

## 6. 통합 테스트

### 6.1 통합 테스트 범위

통합 테스트는 여러 컴포넌트가 함께 동작하는지 검증합니다.

**API 통합 테스트**: GraphQL API 엔드포인트 테스트

**데이터베이스 통합 테스트**: ORM 및 쿼리 동작 테스트

**외부 서비스 통합 테스트**: PG사, 블록체인, 이메일 서비스 연동 테스트

### 6.2 API 통합 테스트

**GraphQL API 테스트**:

```
TC-INT-API-001: 게임 목록 조회 쿼리
- 쿼리: games(filter: {gameType: DAILY}, first: 10)
- 예상 결과: 최대 10개의 DAILY 게임 반환
```

## 16. 결함 관리

### 16.1 결함 우선순위

- 서비스 중단
- 데이터 손실
- 보안 취약점
- 금융 거래 오류

**High (높음)**:
- 주요 기능 불가
- 다수 사용자 영향
- 성능 심각한 저하

처리: 24시간 내 수정, 다음 배포에 포함

**Medium (중간)**:
- 일부 기능 불편
- 소수 사용자 영향
- UI/UX 문제

처리: 다음 스프린트에 수정

**Low (낮음)**:
- 사소한 버그
- 개선 제안
- 문서 오류

## 17. 테스트 완료 기준

### 17.1 Exit Criteria

다음 조건을 모두 만족해야 릴리스 가능합니다:

**기능 테스트**:
- 모든 Critical 및 High 우선순위 테스트 케이스 통과
- Medium 우선순위 90% 이상 통과

**커버리지**:
- 단위 테스트 커버리지 80% 이상
- API 엔드포인트 100% 테스트

**결함**:
- Critical 결함 0건
- High 결함 0건
- Medium 결함 5건 이하

**성능**:
- 평균 응답 시간 200ms 이하
- 95th percentile 500ms 이하
- 부하 테스트 통과

**보안**:
- OWASP Top 10 취약점 없음
- 보안 스캔 Critical/High 이슈 없음

**문서**:
- 테스트 결과 리포트 작성
- 알려진 이슈 목록 문서화

### 17.2 릴리스 체크리스트

```
□ 모든 테스트 케이스 실행 완료
□ 회귀 테스트 통과
□ 성능 테스트 통과
□ 보안 테스트 통과
□ UAT (User Acceptance Test) 완료
□ 릴리스 노트 작성
□ 롤백 계획 수립
□ 모니터링 설정 확인
□ 알림 설정 확인
□ 데이터베이스 마이그레이션 검증
□ 제품 책임자 승인
```

## 18. 테스트 일정 및 리소스

### 18.1 테스트 일정

**개발 단계** (각 스프린트 2주):
- Week 1: 개발 + 단위 테스트 (개발자)
- Week 2: 통합 테스트 + 기능 테스트 (QA)

**릴리스 준비** (2주):
- Week 1: 시스템 테스트, 성능 테스트, 보안 테스트
- Week 2: UAT, 회귀 테스트, 최종 검증

**릴리스 후** (1주):
- 프로덕션 모니터링
- Hot-fix 대응

### 18.2 테스트 리소스

**팀 구성**:
- QA 리드: 1명
- QA 엔지니어: 3명
- 자동화 엔지니어: 1명
- 보안 전문가: 1명 (파트타임)

**인프라**:
- 테스트 서버: AWS EC2 (Staging 환경)
- 테스트 데이터베이스: PostgreSQL (Staging)
- 블록체인: Polygon Mumbai Testnet
- CI/CD: GitHub Actions
- 모니터링: Datadog, Sentry

**도구 라이선스**:
- Jira (팀 전체)
- SonarQube (개발팀)
- Artillery (성능 테스트)
- Appium (모바일 테스트)

### 18.3 위험 관리

**위험 요소**:

| 위험 | 영향 | 확률 | 완화 전략 |
|------|------|------|-----------|
| 블록체인 네트워크 불안정 | 높음 | 중간 | Testnet 먼저 충분히 테스트, Mainnet 전환 시 단계적 |
| PG사 연동 지연 | 중간 | 낮음 | Mock PG 서버로 개발/테스트 병행 |
| 성능 목표 미달성 | 높음 | 중간 | 초기부터 성능 테스트, 병목 지점 조기 발견 |
| 보안 취약점 발견 | 높음 | 중간 | 지속적인 보안 스캔, 전문가 감사 |
| 테스트 리소스 부족 | 중간 | 높음 | 자동화 극대화, 우선순위 조정 |
