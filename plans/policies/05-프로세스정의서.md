# BlockPick 프로세스 정의서

**문서 버전**: 1.0
**작성일**: 2025-11-20
**문서 유형**: 비즈니스 프로세스 명세서

---

## 1. 문서 개요

본 프로세스 정의서는 BlockPick 서비스의 주요 비즈니스 프로세스를 단계별로 상세히 정의합니다. 각 프로세스는 시작 조건, 단계별 작업, 종료 조건, 예외 처리를 포함하며, 모든 이해관계자가 프로세스를 명확히 이해할 수 있도록 문장으로 작성되었습니다.

---

## 2. 회원가입 프로세스

### 2.1 프로세스 개요

회원가입 프로세스는 신규 사용자가 BlockPick 계정을 생성하는 과정입니다. 이메일 인증을 통해 유효한 사용자임을 확인하고, 안전한 비밀번호를 설정하도록 안내합니다.

### 2.2 단계별 상세 설명

**1단계: 회원가입 화면 진입**
사용자가 앱을 처음 실행하면 환영 화면이 표시됩니다. 환영 화면에는 "시작하기" 버튼과 "이미 계정이 있나요? 로그인" 링크가 있습니다. 사용자가 "시작하기" 버튼을 누르면 회원가입 화면으로 이동합니다. 회원가입 화면에는 이메일 입력 필드와 "다음" 버튼이 있습니다.

**2단계: 이메일 입력 및 검증**
사용자가 이메일 주소를 입력합니다. 입력 필드에는 실시간 유효성 검사가 적용되어, 올바른 이메일 형식이 아니면 "유효한 이메일 주소를 입력해주세요"라는 메시지가 표시됩니다. 이메일 형식은 정규식으로 검증되며, "@" 기호와 도메인이 포함되어야 합니다. 사용자가 올바른 형식의 이메일을 입력하고 "다음" 버튼을 누르면, 시스템은 해당 이메일이 이미 등록되어 있는지 확인합니다. 만약 이미 등록된 이메일이라면 "이미 사용 중인 이메일입니다. 로그인하시겠습니까?"라는 메시지와 함께 로그인 화면으로 이동하는 옵션이 제공됩니다.

**3단계: 인증 코드 발송**
이메일이 유효하고 중복되지 않았다면, 시스템은 6자리 숫자로 구성된 인증 코드를 생성합니다. 인증 코드는 무작위로 생성되며, 000000부터 999999 사이의 값입니다. 생성된 코드는 Redis에 저장되며, 키는 이메일 주소, 값은 인증 코드, TTL(Time To Live)은 10분으로 설정됩니다. 동시에 이메일 발송 서비스(SendGrid 또는 AWS SES)를 통해 사용자의 이메일로 인증 코드가 발송됩니다. 이메일 제목은 "[BlockPick] 회원가입 인증 코드"이며, 본문에는 "인증 코드: 123456 (10분간 유효)"와 같은 내용이 포함됩니다. 이메일 발송이 성공하면 사용자에게 "인증 코드를 [email]으로 발송했습니다"라는 메시지가 표시되고, 인증 코드 입력 화면으로 자동 전환됩니다.

**4단계: 인증 코드 입력 및 확인**
인증 코드 입력 화면에는 6개의 입력 필드가 나란히 배치되어 있으며, 각 필드에는 한 자리 숫자만 입력할 수 있습니다. 사용자가 첫 번째 필드에 숫자를 입력하면 자동으로 다음 필드로 포커스가 이동하여 빠른 입력을 돕습니다. 6자리를 모두 입력하면 자동으로 검증이 시작됩니다. 시스템은 입력된 코드를 Redis에 저장된 코드와 비교합니다. 코드가 일치하면 검증 성공으로 처리되고, 일치하지 않으면 "인증 코드가 일치하지 않습니다. 다시 확인해주세요"라는 메시지가 표시됩니다. 사용자는 최대 5회까지 재시도할 수 있으며, 5회 실패 시 "인증 코드 재발송" 버튼이 활성화됩니다. 또한 10분이 경과하면 코드가 만료되어 "인증 코드가 만료되었습니다. 재발송해주세요"라는 메시지가 표시됩니다.

**5단계: 비밀번호 설정**
인증 코드 확인이 성공하면 비밀번호 설정 화면으로 이동합니다. 비밀번호 입력 필드와 비밀번호 확인 필드가 있으며, 두 필드의 값이 일치해야 합니다. 비밀번호는 다음 규칙을 따라야 합니다. 첫째, 최소 8자 이상이어야 합니다. 둘째, 영문 대문자, 영문 소문자, 숫자, 특수문자 중 최소 3가지 이상을 포함해야 합니다. 입력 필드 아래에는 비밀번호 강도 인디케이터가 표시되며, 약함(빨간색), 보통(노란색), 강함(초록색)으로 시각적 피드백을 제공합니다. 사용자가 규칙을 만족하는 비밀번호를 입력하고 확인 필드에도 동일한 값을 입력하면 "다음" 버튼이 활성화됩니다.

**6단계: 기본 정보 입력**
비밀번호 설정이 완료되면 기본 정보 입력 화면으로 이동합니다. 여기서는 이름, 전화번호, 생년월일을 입력합니다. 이름은 2자 이상 20자 이하의 한글, 영문으로 입력할 수 있습니다. 전화번호는 010-1234-5678 형식으로 입력하며, 자동으로 하이픈이 삽입됩니다. 생년월일은 YYYY-MM-DD 형식의 날짜 피커를 통해 선택합니다. 모든 필드를 입력하면 "가입 완료" 버튼이 활성화됩니다.

**7단계: 계정 생성 및 완료**
사용자가 "가입 완료" 버튼을 누르면, 시스템은 다음 작업을 수행합니다. 첫째, 비밀번호를 bcrypt 알고리즘으로 해싱합니다. bcrypt는 자동으로 솔트를 생성하고 해싱 비용을 10 라운드로 설정하여 안전하게 저장합니다. 둘째, users 테이블에 새로운 레코드를 생성합니다. 레코드에는 이메일, 비밀번호 해시, 이름, 전화번호, 생년월일, 생성 일시가 포함됩니다. 셋째, 기본 Event Cash 1,000원을 적립합니다. 이는 환영 보너스로, 사용자가 첫 게임에 바로 참여할 수 있도록 돕습니다. 넷째, 환영 이메일을 발송합니다. 이메일에는 가입 축하 메시지와 함께 BlockPick 서비스 소개, 첫 게임 참여 가이드 링크가 포함됩니다. 모든 작업이 완료되면 "가입이 완료되었습니다!" 메시지와 함께 로그인 화면으로 이동하거나, 자동 로그인 후 메인 홈으로 이동합니다.

### 2.3 예외 처리

**이메일 발송 실패**
인증 코드 이메일 발송이 실패한 경우, 시스템은 최대 3회까지 자동으로 재시도합니다. 재시도 간격은 첫 번째 1초, 두 번째 2초, 세 번째 4초입니다. 모든 재시도가 실패하면 사용자에게 "일시적인 오류로 인증 코드를 발송하지 못했습니다. 잠시 후 다시 시도해주세요"라는 메시지가 표시되며, "재시도" 버튼이 제공됩니다.

**데이터베이스 오류**
계정 생성 중 데이터베이스 오류가 발생하면, 트랜잭션이 롤백되어 부분적으로 생성된 데이터가 없도록 합니다. 사용자에게는 "회원가입 처리 중 오류가 발생했습니다. 고객 지원팀에 문의해주세요"라는 메시지가 표시되며, 에러는 Sentry로 자동 전송되어 개발팀이 즉시 확인할 수 있습니다.

## 3. 로그인 프로세스

### 3.1 프로세스 개요

로그인 프로세스는 등록된 사용자가 이메일과 비밀번호를 사용하여 인증하고, JWT 토큰을 발급받아 서비스에 접근하는 과정입니다.

### 3.2 단계별 상세 설명

**1단계: 로그인 화면 진입**
사용자가 앱을 실행하면 저장된 리프레시 토큰이 있는지 확인합니다. 유효한 리프레시 토큰이 있으면 자동으로 로그인되어 메인 홈으로 이동합니다. 토큰이 없거나 만료되었다면 로그인 화면이 표시됩니다.

**2단계: 인증 정보 입력**
사용자가 이메일과 비밀번호를 입력합니다. 이메일 필드는 키보드 타입이 이메일로 설정되어 "@" 기호에 빠르게 접근할 수 있습니다. 비밀번호 필드는 입력 내용이 가려지며, 눈 아이콘을 탭하면 임시로 보이도록 할 수 있습니다.

**3단계: 로그인 요청**
사용자가 "로그인" 버튼을 누르면, login GraphQL 뮤테이션이 서버로 전송됩니다. 요청에는 이메일과 평문 비밀번호가 포함됩니다.

**4단계: 서버 측 인증**
서버는 먼저 이메일로 users 테이블을 조회합니다. 해당 이메일의 사용자가 존재하지 않으면 "이메일 또는 비밀번호가 일치하지 않습니다"라는 에러를 반환합니다. 사용자가 존재하면 저장된 비밀번호 해시와 입력된 비밀번호를 bcrypt.compare 함수로 비교합니다. 비밀번호가 일치하면 인증 성공이며, 일치하지 않으면 실패 카운트를 증가시킵니다. 연속 5회 실패 시 해당 계정은 15분간 잠기며, "계정이 일시적으로 잠겼습니다. 15분 후 다시 시도하거나 비밀번호를 재설정하세요"라는 메시지가 반환됩니다.

**5단계: 토큰 발급**
인증이 성공하면 서버는 두 개의 JWT 토큰을 발급합니다. 액세스 토큰은 유효기간이 30분이며, 페이로드에 userId, email, role이 포함됩니다. 리프레시 토큰은 유효기간이 7일이며, 무작위 생성된 토큰 ID만 포함됩니다. 리프레시 토큰은 데이터베이스의 refresh_tokens 테이블에 저장되어, 나중에 검증할 수 있습니다.

**6단계: 클라이언트 저장**
클라이언트는 받은 토큰을 안전하게 저장합니다. 액세스 토큰은 메모리에 저장되어 앱이 실행되는 동안 사용되며, 리프레시 토큰은 Flutter Secure Storage에 암호화되어 저장됩니다. 이후 모든 API 요청에는 액세스 토큰이 Authorization 헤더에 "Bearer [token]" 형태로 포함됩니다.

**7단계: 로그인 완료**
토큰 저장이 완료되면 사용자는 메인 홈 화면으로 이동합니다. 백그라운드에서는 사용자 프로필, 보유 Cash, 최근 참여 게임 등의 데이터를 비동기로 로드합니다.

## 4. 게임 참가 프로세스

### 4.1 프로세스 개요

게임 참가 프로세스는 BlockPick의 가장 핵심적인 프로세스입니다. 사용자가 게임을 선택하고, 그리드에서 블록을 선택하며, 블록체인에 참여 기록을 남기고, 참가비를 결제하는 전 과정을 포함합니다.

### 4.2 단계별 상세 설명

**1단계: 로그인 확인**
사용자가 게임 상세 화면에서 "참가하기" 버튼을 누르면, 시스템은 먼저 사용자의 로그인 상태를 확인합니다. 액세스 토큰이 유효한지 검증하며, 만료되었다면 리프레시 토큰을 사용하여 새로운 액세스 토큰을 발급받습니다. 만약 리프레시 토큰도 만료되었다면 로그인 화면으로 이동하며, "다시 로그인해주세요" 메시지가 표시됩니다.

**2단계: 게임 정보 조회**
로그인이 확인되면 getGameById GraphQL 쿼리를 통해 최신 게임 정보를 조회합니다. 이는 사용자가 게임 화면에 진입한 후 정보가 변경되었을 수 있기 때문입니다. 조회된 정보에는 현재 참여자 수, 남은 블록 수, 게임 상태가 포함됩니다. 만약 게임이 이미 종료되었거나 참여자 수가 최대에 도달했다면 "이 게임은 더 이상 참가할 수 없습니다"라는 메시지와 함께 프로세스가 중단됩니다.

**3단계: 게임 플레이 화면 진입**
게임 참가가 가능하다면 게임 플레이 화면으로 전환됩니다. 이 화면의 중앙에는 1,000×1,000 크기의 그리드가 표시됩니다. 그리드는 CustomPaint 위젯을 사용하여 렌더링되며, 초기 줌 레벨은 전체 그리드가 화면에 보이도록 설정됩니다. 상단에는 게임명과 참가비가 표시되고, 하단에는 현재 선택한 블록 수와 "참가하기" 버튼이 있습니다. 우측 상단에는 미니맵이 작은 사각형으로 표시되어, 전체 그리드에서 현재 보고 있는 위치를 표시합니다.

**4단계: 블록 선택**
사용자는 그리드에서 정확히 9개의 블록을 선택해야 합니다. 선택 방법은 다음과 같습니다. 첫째, 사용자가 손가락으로 그리드의 특정 위치를 터치합니다. 둘째, 시스템은 터치된 화면 좌표를 그리드 좌표로 변환합니다. 예를 들어 화면 좌표 (100, 200)이 그리드 좌표 (345, 678)에 해당할 수 있습니다. 셋째, 해당 좌표를 중심으로 3×3 영역이 선택됩니다. 즉, 사용자가 (345, 678)을 선택하면 (344, 677)부터 (346, 679)까지의 9개 블록이 모두 선택됩니다. 선택된 블록은 시각적으로 강조 표시되며, 보라색 테두리와 반투명 보라색 배경이 적용됩니다. 동시에 햅틱 피드백(진동)이 발생하여 촉각적으로도 선택을 확인할 수 있습니다. 넷째, 선택 완료 후 하단의 카운터가 "선택: 9/9 블록"으로 업데이트되고, "참가하기" 버튼이 활성화됩니다.

블록 선택에는 제약사항이 있습니다. 이미 다른 사용자가 선택한 블록은 회색으로 표시되며 선택할 수 없습니다. 터치 시 "이미 선택된 블록입니다"라는 토스트 메시지가 표시됩니다. 또한 그리드 경계를 벗어나는 블록은 선택할 수 없습니다. 예를 들어 (999, 999)를 선택하면 3×3 영역이 그리드를 벗어나므로 선택이 불가능합니다.

사용자는 선택을 취소하고 다른 블록을 선택할 수 있습니다. 이미 선택된 영역을 다시 터치하면 선택이 해제되며, 다시 빈 상태로 돌아갑니다. 선택 횟수에는 제한이 없으므로, 사용자는 원하는 만큼 여러 위치를 시도해볼 수 있습니다.

그리드 탐색을 돕기 위해 확대/축소와 이동 기능이 제공됩니다. 사용자는 pinch 제스처로 그리드를 확대하거나 축소할 수 있습니다. 최소 0.01배(전체 그리드가 한눈에)부터 최대 8배(개별 블록이 크게)까지 가능합니다. 또한 드래그 제스처로 그리드를 이동할 수 있습니다. 미니맵을 탭하면 해당 위치로 즉시 이동합니다.

**5단계: 잔액 확인**
사용자가 "참가하기" 버튼을 누르면, 시스템은 먼저 Event Cash 잔액을 확인합니다. getUserCash 쿼리를 통해 현재 보유한 Event Cash와 Shopping Cash를 조회합니다. 참가비가 3,000원인데 Event Cash가 2,500원이라면, 500원이 부족합니다. 이 경우 "Event Cash가 부족합니다. 충전하시겠습니까?"라는 팝업이 표시되며, "충전하기"와 "취소" 버튼이 제공됩니다. 사용자가 "충전하기"를 선택하면 충전 화면으로 이동합니다. "취소"를 선택하면 게임 화면으로 돌아갑니다. 잔액이 충분하다면 다음 단계로 진행합니다.

**6단계: 지갑 확인 및 생성**
시스템은 사용자의 블록체인 지갑이 있는지 확인합니다. users 테이블의 walletAddress 컬럼을 조회하며, null이 아니면 기존 지갑을 사용합니다. walletAddress가 null이면 새로운 지갑을 생성해야 합니다.

지갑 생성 프로세스는 클라이언트에서 수행됩니다. 첫째, BIP39 표준에 따라 12단어의 니모닉 문구를 생성합니다. 니모닉은 영어 단어 목록에서 무작위로 선택되며, 예를 들어 "apple banana cherry dog elephant ... zebra"와 같은 형태입니다. 둘째, 니모닉으로부터 시드를 생성합니다. 시드는 64바이트의 바이너리 데이터입니다. 셋째, 시드에서 개인키를 유도합니다. BIP44 경로(m/44'/60'/0'/0/0)를 사용하여 Ethereum 호환 개인키를 생성합니다. 넷째, 개인키로부터 공개키를 계산하고, 공개키를 해싱하여 지갑 주소를 얻습니다. 주소는 0x로 시작하는 40자리 16진수 문자열입니다. 다섯째, 개인키를 Flutter Secure Storage에 AES-256으로 암호화하여 저장합니다. 여섯째, 지갑 주소를 서버로 전송하여 users 테이블의 walletAddress 컬럼을 업데이트합니다.

지갑 생성은 사용자가 인지하지 못하는 사이에 백그라운드에서 수행됩니다. 진행 표시기가 "게임 참가 준비 중..."이라는 메시지와 함께 표시되며, 일반적으로 1-2초 내에 완료됩니다.

**7단계: 좌표 암호화**
선택한 블록의 좌표를 암호화합니다. 암호화는 다른 참여자가 내 선택을 미리 알 수 없도록 보호하기 위함입니다. 암호화 과정은 다음과 같습니다.

첫째, 서버로부터 암호화 키를 요청합니다. getGameEncryptionKey 쿼리를 통해 해당 게임의 고유 암호화 키를 받습니다. 키는 Base64로 인코딩된 32바이트 AES-256 키입니다. 둘째, 선택한 9개 블록의 좌표를 문자열로 변환합니다. 예를 들어 [(123, 456), (124, 456), (125, 456), (123, 457), (124, 457), (125, 457), (123, 458), (124, 458), (125, 458)]를 "123,456;124,456;125,456;..." 형태로 직렬화합니다. 셋째, 16바이트의 무작위 IV(Initialization Vector)를 생성합니다. IV는 동일한 평문을 암호화해도 매번 다른 암호문이 나오도록 합니다. 넷째, AES-256-CBC 모드로 좌표 문자열을 암호화합니다. 암호화 라이브러리는 encrypt 패키지를 사용합니다. 다섯째, IV와 암호문을 결합하여 Base64로 인코딩합니다. 최종 암호화된 데이터는 약 200-300바이트의 문자열입니다.

**8단계: 지갑 주소 해싱**
사용자의 지갑 주소를 SHA-256 알고리즘으로 해싱합니다. 해싱 이유는 블록체인에 개인 정보를 노출하지 않기 위함입니다. 지갑 주소 자체는 익명이지만, 여러 트랜잭션을 연결하면 사용자를 추적할 수 있으므로, 해시로 변환하여 추가 보호 계층을 제공합니다. 해싱은 클라이언트에서 수행되며, 지갑 주소를 소문자로 변환한 후 SHA-256을 적용합니다. 결과는 64자리 16진수 문자열입니다.

**9단계: 블록체인 트랜잭션 생성**
이제 스마트 컨트랙트의 participateInGame 함수를 호출하는 트랜잭션을 생성합니다. 트랜잭션 파라미터는 다음과 같습니다. gameId는 게임의 고유 식별자, encryptedCoordinates는 8단계에서 생성한 암호화된 좌표, hashedWalletAddress는 9단계에서 생성한 해시입니다.

트랜잭션은 서버에서 구성됩니다. 서버는 web3.js 또는 ethers.js 라이브러리를 사용하여 트랜잭션 객체를 생성합니다. 트랜잭션에는 컨트랙트 주소, 함수 호출 데이터(ABI 인코딩), 가스 한도, 가스 가격이 포함됩니다. 가스 한도는 과거 트랜잭션 데이터를 기반으로 추정되며, 일반적으로 150,000 가스 정도입니다. 가스 가격은 Polygon 네트워크의 현재 가스 가격을 조회하여 설정하며, 빠른 처리를 위해 평균보다 약간 높게 설정합니다.

구성된 트랜잭션은 클라이언트로 전송됩니다. 클라이언트는 사용자의 개인키로 트랜잭션에 서명합니다. 서명은 ECDSA(Elliptic Curve Digital Signature Algorithm)를 사용하며, 개인키가 외부로 노출되지 않습니다. 서명된 트랜잭션은 raw transaction 형태로 직렬화됩니다.

**10단계: 블록체인 전송**
서명된 트랜잭션을 Polygon 네트워크로 전송합니다. 클라이언트는 Polygon RPC 엔드포인트에 eth_sendRawTransaction JSON-RPC 호출을 보냅니다. 네트워크는 트랜잭션을 받아 멤풀(mempool)에 추가하고, 트랜잭션 해시를 즉시 반환합니다. 트랜잭션 해시는 66자리 16진수 문자열로, 예를 들어 "0x1234567890abcdef..."입니다.

트랜잭션이 블록에 포함될 때까지 기다립니다. Polygon은 평균 2초마다 블록을 생성하므로, 일반적으로 2-4초 내에 트랜잭션이 확인됩니다. 클라이언트는 주기적으로 eth_getTransactionReceipt를 호출하여 트랜잭션 상태를 폴링합니다. 트랜잭션 영수증이 반환되고 status 필드가 1이면 성공, 0이면 실패입니다. 실패한 경우 revertReason을 확인하여 에러 원인을 파악합니다. 일반적인 실패 원인은 가스 부족, 컨트랙트 로직 에러(예: 이미 선택된 블록), 네트워크 혼잡 등입니다.

**11단계: 참가비 차감**
블록체인 트랜잭션이 성공하면, 서버는 참가비를 사용자의 Event Cash에서 차감합니다. deductCash 뮤테이션을 내부적으로 호출하며, 파라미터는 userId, amount, type(게임 참가)입니다. 데이터베이스 트랜잭션을 시작하고, 다음 쿼리를 순차적으로 실행합니다. 첫째, users 테이블의 eventCash 컬럼을 차감합니다. 예를 들어 eventCash가 5,000원이고 참가비가 3,000원이면, UPDATE users SET eventCash = eventCash - 3000 WHERE id = userId를 실행합니다. 둘째, transactions 테이블에 거래 기록을 추가합니다. type은 'USE', amount는 3,000, description은 '게임 참가: [게임명]', relatedGameId는 해당 게임 ID입니다. 모든 쿼리가 성공하면 트랜잭션을 커밋하고, 하나라도 실패하면 롤백합니다.

**12단계: 참여 내역 저장**
participations 테이블에 새로운 레코드를 추가합니다. 레코드는 다음 정보를 포함합니다. userId는 참여한 사용자의 ID, gameId는 게임 ID, selectedBlocks는 9개 좌표의 JSON 배열, encryptedCoordinates는 암호화된 좌표, transactionHash는 블록체인 트랜잭션 해시, participatedAt은 현재 타임스탬프, isWinner는 초기값 false, refundAmount는 초기값 0입니다.

**13단계: 참가 완료 알림**
모든 처리가 성공하면 사용자에게 참가 완료 메시지를 표시합니다. 화면 중앙에 축하 애니메이션과 함께 "게임 참가 완료!" 메시지가 나타납니다. 애니메이션은 Lottie를 사용한 폭죽 효과입니다. 하단에는 "선택한 블록: (123, 456) 외 8개", "참가비: 3,000원", "트랜잭션: 0x1234..." 정보가 표시됩니다. "My Pick에서 확인하기" 버튼을 누르면 My Pick 화면으로 이동하여 방금 참여한 게임을 확인할 수 있습니다.

백그라운드에서는 게임의 currentParticipants 수를 1 증가시키고, 선택된 블록을 occupied 상태로 표시하여 다른 사용자가 선택할 수 없도록 합니다. 게임 목록과 상세 화면을 구독하고 있는 다른 사용자에게는 WebSocket을 통해 실시간으로 참여자 수 변경이 푸시됩니다.

### 4.3 예외 처리

**네트워크 오류**
게임 참가 중 네트워크 연결이 끊어지면, 시스템은 현재 단계를 저장하고 연결 복구 시 재시도합니다. 예를 들어 블록체인 전송 직전에 연결이 끊어졌다면, 연결 복구 후 트랜잭션 전송부터 재개합니다. 이미 전송된 트랜잭션이 있는지 확인하기 위해 트랜잭션 해시를 로컬 저장소에 저장합니다.

**블록 선택 충돌**
사용자가 블록을 선택하고 참가하기를 누르는 사이에 다른 사용자가 동일한 블록을 선택할 수 있습니다. 이 경우 스마트 컨트랙트는 "Already occupied" 에러를 반환합니다. 사용자에게는 "선택하신 블록이 이미 다른 사용자에게 선택되었습니다. 다른 블록을 선택해주세요"라는 메시지가 표시되며, 게임 화면으로 돌아갑니다. 차감된 참가비는 즉시 환불됩니다.

**잔액 부족 (Race Condition)**
블록 선택 후 참가비 차감 전에 사용자가 다른 디바이스에서 Event Cash를 사용한 경우, 잔액이 부족할 수 있습니다. 이 경우 "Event Cash 잔액이 부족합니다. 현재 잔액: [금액]" 메시지가 표시되며, 충전 화면으로 이동하는 옵션이 제공됩니다.

**트랜잭션 실패**
블록체인 트랜잭션이 실패하는 경우는 드물지만, 가스 부족이나 네트워크 오류로 발생할 수 있습니다. 트랜잭션 실패 시 자동으로 1회 재시도하며, 재시도도 실패하면 사용자에게 "일시적인 오류로 게임 참가에 실패했습니다. 고객 지원팀에 문의해주세요. 참가비는 환불됩니다"라는 메시지가 표시됩니다. 차감된 참가비는 자동으로 환불되며, 환불 내역은 거래 내역에 기록됩니다.

## 5. 당첨자 선정 프로세스

### 5.1 프로세스 개요

당첨자 선정 프로세스는 게임 종료 후 자동으로 실행되며, 블록체인의 검증 가능한 랜덤 함수를 사용하여 공정하게 당첨 블록을 결정하고, 해당 블록을 선택한 참여자를 찾아 당첨자로 지정합니다.

### 5.2 단계별 상세 설명

**1단계: 게임 종료 감지**
크론 작업(Cron Job)이 매분마다 실행되어 종료된 게임을 찾습니다. 현재 시각이 게임의 endDate를 초과하고, status가 ONGOING인 게임을 조회합니다. 종료된 게임이 발견되면 당첨자 선정 작업을 큐에 추가합니다.

**2단계: 게임 상태 변경**
게임의 status를 ENDED로 변경하여, 더 이상 참여할 수 없도록 합니다. 동시에 참가 취소도 불가능하게 됩니다.

**3단계: Chainlink VRF 요청**
스마트 컨트랙트의 requestRandomness 함수를 호출하여 Chainlink VRF에 랜덤 숫자를 요청합니다. VRF(Verifiable Random Function)는 검증 가능한 난수 생성 함수로, 생성된 난수가 조작되지 않았음을 암호학적으로 증명할 수 있습니다. 요청에는 requestId가 포함되며, 이는 나중에 응답을 매칭하는 데 사용됩니다.

**4단계: 랜덤 숫자 수신**
Chainlink 노드는 블록 해시와 비밀 키를 사용하여 난수를 생성하고, 증명(proof)과 함께 스마트 컨트랙트로 전송합니다. 스마트 컨트랙트는 증명을 검증하여 난수가 올바르게 생성되었는지 확인합니다. 검증이 통과되면 난수를 저장하고, RandomnessFulfilled 이벤트를 발생시킵니다.

**5단계: 당첨 블록 결정**
받은 난수를 사용하여 0부터 999,999 사이의 숫자를 생성합니다. 이 숫자를 1,000으로 나눈 몫이 x 좌표, 나머지가 y 좌표가 됩니다. 예를 들어 난수가 456,789라면 x = 456, y = 789입니다. 이 좌표를 중심으로 한 3×3 섹션이 당첨 블록이 됩니다.

**6단계: 당첨자 찾기**
participations 테이블을 조회하여 당첨 블록과 일치하는 selectedBlocks를 가진 참여자를 찾습니다. selectedBlocks는 JSON 배열이므로, JSON 함수를 사용하여 쿼리합니다. 예를 들어 PostgreSQL에서는 SELECT * FROM participations WHERE gameId = ? AND selectedBlocks @> '[{"x": 456, "y": 789}]'과 같은 쿼리를 사용합니다.

만약 정확히 일치하는 참여자가 없다면, 가장 가까운 블록을 선택한 참여자를 찾습니다. 거리 계산은 유클리드 거리를 사용합니다. 모든 참여자의 블록과 당첨 블록 사이의 거리를 계산하고, 가장 짧은 거리를 가진 참여자를 당첨자로 선정합니다.

만약 여러 참여자가 동일한 거리를 가지면, 그 중에서 다시 랜덤으로 선택합니다. 이때는 블록체인 난수를 재사용하여 참여자 배열의 인덱스를 결정합니다.

**7단계: 당첨자 지정**
당첨자가 결정되면 다음 작업을 수행합니다. 첫째, participations 테이블의 해당 레코드에서 isWinner를 true로 설정합니다. 둘째, games 테이블의 winnerId를 당첨자의 userId로 설정하고, winningBlocks를 당첨 블록 좌표로 저장합니다. 셋째, 스마트 컨트랙트의 setWinner 함수를 호출하여 블록체인에도 당첨자를 기록합니다.

**8단계: 알림 발송**
모든 참여자에게 결과 알림을 발송합니다. 당첨자에게는 "축하합니다! [게임명]에서 당첨되셨습니다!"라는 제목의 푸시 알림, 이메일, SMS를 전송합니다. 알림에는 상품명, 수령 방법 안내 링크가 포함됩니다. 낙첨자에게는 "아쉽게도 이번에는 당첨되지 않았습니다. Event Cash [금액]이 환급되었습니다"라는 알림을 전송합니다.

**9단계: Event Cash 환급**
낙첨자에게는 참가비의 일부를 Event Cash로 환급합니다. 환급 비율은 게임 타입에 따라 다릅니다. DAILY는 10%, SELECT는 20%, VIBE는 30%입니다. 예를 들어 SELECT 게임에 3,000원으로 참가한 낙첨자는 600원을 환급받습니다. 환급은 자동으로 처리되며, users 테이블의 eventCash를 증가시키고, transactions 테이블에 환급 기록을 추가합니다.

**10단계: 통계 업데이트**
게임 통계를 업데이트합니다. 총 참여자 수, 총 참가비, 환급 금액, 당첨 블록, 당첨자 ID 등을 집계하여 game_statistics 테이블에 저장합니다. 이는 추후 분석에 사용됩니다.

## 6. Event Cash 충전 프로세스

### 6.1 단계별 상세 설명

**1단계: 충전 화면 진입**
사용자가 My 페이지에서 "충전하기" 버튼을 누르거나, 게임 참가 시 잔액 부족으로 인해 자동으로 충전 화면으로 이동합니다.

**2단계: 금액 선택**
충전 금액을 선택합니다. 빠른 선택 버튼으로 1,000원, 5,000원, 10,000원, 50,000원이 제공되며, "직접 입력"을 선택하면 원하는 금액을 입력할 수 있습니다. 최소 충전 금액은 1,000원, 최대는 500,000원이며, 1,000원 단위로만 입력 가능합니다.

**3단계: 결제 수단 선택**
신용카드, 체크카드, 계좌이체 중 하나를 선택합니다. 선택한 결제 수단에 따라 PG사의 결제 화면이 표시됩니다.

**4단계: 결제 진행**
토스페이먼츠 SDK를 통해 결제 화면이 WebView 또는 별도 창으로 열립니다. 사용자는 카드 정보를 입력하거나 계좌를 선택하여 결제를 진행합니다. 결제 중에는 BlockPick 서버와 PG사 서버 간 통신이 발생하지 않으며, 모든 결제 정보는 PG사에서만 처리됩니다.

**5단계: 결제 완료 콜백**
결제가 완료되면 PG사는 BlockPick 서버의 웹훅 URL로 결제 결과를 전송합니다. 웹훅 데이터에는 결제 ID, 금액, 상태, 사용자 ID가 포함됩니다. 서버는 결제 ID로 PG사에 결제 확인 API를 호출하여 실제로 결제가 성공했는지 이중 검증합니다. 이는 웹훅이 위조되는 것을 방지하기 위함입니다.

**6단계: Event Cash 적립**
결제가 확인되면 users 테이블의 eventCash를 증가시킵니다. 동시에 transactions 테이블에 충전 기록을 추가합니다. type은 'CHARGE', amount는 충전 금액, description은 '카드 결제 충전', paymentId는 PG사 결제 ID입니다.

**7단계: 충전 완료**
클라이언트에는 WebView의 리턴 URL을 통해 결과가 전달됩니다. 충전 성공 시 "충전이 완료되었습니다! 현재 잔액: [금액]"이라는 메시지와 함께 이전 화면으로 돌아갑니다. 게임 참가 중이었다면 게임 화면으로 돌아가 바로 참가할 수 있습니다.
