## 1. 홈 화면 (Home Screen)

### 1.1 화면 구성

- 홈 화면은 상단에 4개의 탭을 가지고 있다
- 탭은 'DAILY', 'SELECT', 'VIBE', 'OPTIMAL'로 구성되어 있다
- 각 탭은 서로 다른 게임 타입을 표시한다

### 1.2 사용자 행동 시나리오

#### 시나리오 1: 앱 최초 실행
1. 사용자가 앱을 실행한다
2. 시스템은 홈 화면을 표시한다
3. 시스템은 기본적으로 'DAILY' 탭을 활성화 상태로 표시한다
4. 시스템은 DAILY 타입 게임 목록을 로드하여 표시한다

#### 시나리오 2: 탭 전환
1. 사용자가 'SELECT' 탭을 클릭한다
2. 시스템은 'SELECT' 탭을 활성화 상태로 표시한다
3. 시스템은 탭 하단에 파란색(#5C72F5) 인디케이터를 표시한다
4. 시스템은 SELECT 타입 게임 목록을 로드하여 표시한다

#### 시나리오 3: VIBE 탭 선택
1. 사용자가 'VIBE' 탭을 클릭한다
2. 시스템은 'VIBE' 탭을 활성화 상태로 표시한다
3. 시스템은 VIBE 타입 게임 목록을 로드하여 표시한다

#### 시나리오 4: OPTIMAL 탭 선택
1. 사용자가 'OPTIMAL' 탭을 클릭한다
2. 시스템은 'OPTIMAL' 탭을 활성화 상태로 표시한다
3. 시스템은 최적가 게임 목록을 로드하여 표시한다 (다른 탭과 레이아웃이 다름)

### 1.3 시스템 동작

- 탭 전환 시 TabController가 선택된 탭 인덱스를 관리한다
- 각 탭은 독립적인 GameListScreen 또는 OptimalGameListScreen 위젯을 표시한다
- 탭 전환 시 애니메이션 효과가 적용된다

## 2. 게임 목록 화면 (Game List Screen)

### 2.1 화면 구성

- 상단에 배너 영역이 있다
- 배너 아래에 필터 바가 있다
- 필터 바에는 카테고리 필터 칩들이 있다
- 필터 바 하단에는 정렬 드롭다운과 게임 개수가 표시된다
- 하단에는 게임 카드 그리드가 표시된다

### 2.2 사용자 행동 시나리오

#### 시나리오 1: 게임 목록 최초 로딩
1. 사용자가 게임 목록 화면에 진입한다
2. 시스템은 배너를 표시한다 (Purple → Blue 그라데이션 배경)
3. 시스템은 배너에 "PICK YOUR PRIZE, MAKE IT YOURS" 텍스트를 표시한다
4. 시스템은 로딩 인디케이터를 표시한다
5. 시스템은 GraphQL API를 통해 게임 데이터를 요청한다
6. 시스템은 로딩이 완료되면 게임 카드 그리드를 표시한다
7. 시스템은 필터 바에 게임 개수를 표시한다 (예: "12 games")

#### 시나리오 2: 카테고리 필터 선택
1. 사용자가 'Digital' 카테고리 칩을 클릭한다
2. 시스템은 'Digital' 칩을 선택 상태로 표시한다 (파란색 배경, 흰색 텍스트)
3. 시스템은 이전에 선택된 칩의 선택 상태를 해제한다
4. 시스템은 Digital 카테고리에 해당하는 게임만 필터링하여 표시한다
5. 시스템은 필터 바에 필터링된 게임 개수를 업데이트한다 (예: "5 games")

#### 시나리오 3: 'ALL' 카테고리 선택
1. 사용자가 'ALL' 카테고리 칩을 클릭한다
2. 시스템은 'ALL' 칩을 선택 상태로 표시한다
3. 시스템은 모든 카테고리의 게임을 표시한다
4. 시스템은 전체 게임 개수를 표시한다

#### 시나리오 4: 정렬 옵션 변경
1. 사용자가 정렬 드롭다운을 클릭한다
2. 시스템은 팝업 메뉴를 표시한다
3. 시스템은 4가지 정렬 옵션을 표시한다:
   - Most Popular
   - Newest
   - Ending Soon
   - Price Low to High
4. 사용자가 'Newest' 옵션을 선택한다
5. 시스템은 팝업 메뉴를 닫는다
6. 시스템은 드롭다운 라벨을 'Newest'로 변경한다
7. 시스템은 게임 목록을 최신순으로 재정렬하여 표시한다

#### 시나리오 5: 게임 카드 클릭
1. 사용자가 게임 카드를 클릭한다
2. 시스템은 콘솔에 로그를 출력한다 (게임 ID, 이미지 URL 등)
3. 시스템은 GoRouter를 사용하여 '/game/{gameId}' 경로로 이동한다
4. 시스템은 게임 화면을 표시한다

#### 시나리오 6: 로딩 중 상태
1. 사용자가 게임 목록 화면에 진입한다
2. 시스템은 중앙에 파란색 CircularProgressIndicator를 표시한다
3. 시스템은 데이터 로딩이 완료될 때까지 로딩 인디케이터를 유지한다

#### 시나리오 7: 에러 발생 시
1. 시스템이 게임 데이터 로드에 실패한다
2. 시스템은 중앙에 빨간색 경고 아이콘을 표시한다
3. 시스템은 "Error loading games" 메시지를 표시한다
4. 시스템은 에러 세부 내용을 표시한다
5. 시스템은 파란색 "Retry" 버튼을 표시한다
6. 사용자가 "Retry" 버튼을 클릭한다
7. 시스템은 게임 데이터를 다시 요청한다

#### 시나리오 8: 빈 결과
1. 사용자가 특정 카테고리를 선택한다
2. 시스템은 해당 카테고리에 게임이 없음을 감지한다
3. 시스템은 중앙에 회색 inbox 아이콘을 표시한다
4. 시스템은 "No games found" 메시지를 표시한다
5. 시스템은 "Try changing your filters" 안내 메시지를 표시한다

### 2.3 게임 카드 상세 동작

#### 게임 카드 정보 표시
- 시스템은 각 게임 카드에 다음 정보를 표시한다:
  - 상품 이미지 (16:9 비율)
  - 게임 상태 배지 (좌측 상단): Active/Drawing/Ended
  - 게임 타입 배지 (우측 상단): Daily/Select/Vibe
  - 게임 제목 (최대 2줄, 초과 시 말줄임표)
  - 참가자 수 (아이콘 + 숫자)
  - 총 블록 수 (K/M 단위로 포맷팅)
  - 필요 Pick 수
  - 당첨자 수
  - 원가 (할인이 있는 경우 취소선 표시)
  - 현재가 (파란색, 굵은 글씨)
  - 남은 시간 (시계 아이콘 + 텍스트)

#### 이미지 로딩 처리
1. 시스템은 게임 카드가 화면에 표시될 때 이미지 로드를 시작한다
2. 시스템은 이미지 로딩 중 회색 배경과 CircularProgressIndicator를 표시한다
3. 시스템은 이미지 로드가 완료되면 실제 이미지를 표시한다
4. 시스템은 이미지 로드 실패 시 회색 배경과 이미지 아이콘을 표시한다

## 3. 게임 화면 (Game Screen)

### 3.1 화면 구성

- 상단 우측에 미니맵이 있다
- 상단 좌측에 Pick HUD가 있다 (선택된 블록 수 표시)
- 우측 하단에 줌 컨트롤 버튼이 있다 (+ / -)
- 중앙에 게임 그리드가 있다
- 하단에 선택된 블록 바텀시트가 있다 (블록 선택 시)

### 3.2 사용자 행동 시나리오

#### 시나리오 1: 게임 화면 최초 진입
1. 사용자가 게임 카드를 클릭하여 게임 화면에 진입한다
2. 시스템은 URL에서 gameId를 추출한다
3. 시스템은 GraphQL API를 통해 게임 전체 정보를 요청한다
4. 시스템은 로딩 인디케이터를 표시한다
5. 시스템은 게임 데이터 로드가 완료되면 다음을 수행한다:
   - 그리드 크기를 설정한다 (예: 1000x1000)
   - GridConfig를 생성한다
   - Zoom Spec을 계산한다
   - 3x3 섹션을 생성한다
   - 그리드 중앙을 화면 중앙에 배치한다
   - 초기 줌 레벨을 설정한다
6. 시스템은 미니맵을 표시한다
7. 시스템은 Pick HUD를 표시한다 (0/5 picks)
8. 시스템은 줌 컨트롤 버튼을 표시한다
9. 시스템은 게임 그리드를 표시한다

#### 시나리오 2: 그리드에서 블록 선택
1. 사용자가 그리드에서 특정 블록을 탭한다
2. 시스템은 탭한 위치의 좌표를 계산한다
3. 시스템은 해당 좌표에 해당하는 블록을 선택 상태로 변경한다
4. 시스템은 블록에 파란색 테두리를 표시한다
5. 시스템은 GridStateProvider의 selectedBlocks 리스트에 블록을 추가한다
6. 시스템은 Pick HUD를 업데이트한다 (예: 1/5 picks)
7. 시스템은 하단에 선택 블록 바텀시트를 표시한다
8. 시스템은 바텀시트에 선택된 블록 정보를 표시한다

#### 시나리오 3: 이미 선택된 블록 다시 탭
1. 사용자가 이미 선택된 블록을 다시 탭한다
2. 시스템은 해당 블록의 선택 상태를 해제한다
3. 시스템은 블록의 파란색 테두리를 제거한다
4. 시스템은 GridStateProvider의 selectedBlocks 리스트에서 블록을 제거한다
5. 시스템은 Pick HUD를 업데이트한다 (예: 0/5 picks)
6. 시스템은 선택된 블록이 없으면 바텀시트를 숨긴다

#### 시나리오 4: 최대 Pick 수 초과 선택
1. 사용자가 이미 5개 블록을 선택한 상태에서 6번째 블록을 탭한다
2. 시스템은 선택을 거부한다
3. 시스템은 SnackBar를 표시한다: "최대 5개까지 선택 가능합니다"

#### 시나리오 5: 줌 인 (확대)
1. 사용자가 우측 하단의 '+' 버튼을 클릭한다
2. 시스템은 디바운서를 체크한다 (500ms 내 중복 클릭 방지)
3. 시스템은 현재 줌 레벨이 최대 레벨인지 확인한다
4. 시스템은 줌 레벨을 1단계 증가시킨다
5. 시스템은 뷰포트 중심을 기준으로 줌 인 애니메이션을 수행한다
6. 시스템은 그리드를 확대하여 표시한다
7. 시스템은 미니맵에 현재 뷰포트 위치를 업데이트한다

#### 시나리오 6: 최대 줌 레벨에서 줌 인 시도
1. 사용자가 최대 줌 레벨에서 '+' 버튼을 클릭한다
2. 시스템은 SnackBar를 표시한다: "최대 확대입니다"
3. 시스템은 줌 레벨을 변경하지 않는다

#### 시나리오 7: 줌 아웃 (축소)
1. 사용자가 우측 하단의 '-' 버튼을 클릭한다
2. 시스템은 디바운서를 체크한다
3. 시스템은 현재 줌 레벨이 최소 레벨인지 확인한다
4. 시스템은 줌 레벨을 1단계 감소시킨다
5. 시스템은 뷰포트 중심을 기준으로 줌 아웃 애니메이션을 수행한다
6. 시스템은 그리드를 축소하여 표시한다
7. 시스템은 미니맵에 현재 뷰포트 위치를 업데이트한다

#### 시나리오 8: 최소 줌 레벨에서 줌 아웃 시도
1. 사용자가 최소 줌 레벨에서 '-' 버튼을 클릭한다
2. 시스템은 SnackBar를 표시한다: "최소 축소입니다"
3. 시스템은 줌 레벨을 변경하지 않는다

#### 시나리오 9: 그리드 드래그 (팬)
1. 사용자가 그리드 위에서 드래그 제스처를 시작한다
2. 시스템은 드래그 델타 값을 계산한다
3. 시스템은 현재 pan 위치에 델타를 더한다
4. 시스템은 그리드를 새로운 위치로 이동한다
5. 시스템은 미니맵에 현재 뷰포트 위치를 업데이트한다
6. 사용자가 드래그를 종료한다
7. 시스템은 최종 pan 위치를 저장한다

#### 시나리오 10: 미니맵에서 위치 이동
1. 사용자가 미니맵을 탭한다
2. 시스템은 탭한 위치를 그리드 좌표로 변환한다
3. 시스템은 해당 좌표가 화면 중앙에 오도록 pan 값을 계산한다
4. 시스템은 애니메이션과 함께 그리드를 이동한다
5. 시스템은 미니맵의 뷰포트 박스 위치를 업데이트한다

#### 시나리오 11: 섹션 오버레이 표시
1. 사용자가 그리드를 탐색한다
2. 시스템은 현재 뷰포트에 포함된 섹션을 계산한다
3. 시스템은 각 섹션에 반투명 라벨을 표시한다 (예: "A1", "B2")
4. 사용자가 다른 영역으로 이동한다
5. 시스템은 섹션 라벨을 업데이트한다

### 3.3 그리드 렌더링 동작

- 시스템은 CustomPaint를 사용하여 그리드를 렌더링한다
- 시스템은 LOD (Level of Detail) 시스템을 적용한다:
  - 확대 시: 개별 셀 경계선 표시
  - 축소 시: 경계선 숨김, 성능 최적화

2. 시스템은 GridStateProvider의 clearBlocks() 메서드를 호출한다
3. 시스템은 모든 선택된 블록의 선택 상태를 해제한다
4. 시스템은 그리드에서 파란색 테두리를 제거한다

## 5. 게임 참가 로딩 오버레이

### 5.1 화면 구성

- 전체 화면을 덮는 오버레이이다
- 배경은 Blue → Purple 그라데이션이다

- 단계 표시 (예: 3/5)가 있다
- 하단에 안내 메시지가 있다

### 5.2 사용자 행동 시나리오

#### 시나리오 1: 로딩 오버레이 표시
1. 시스템은 GameJoinLoadingOverlay.show(context)를 호출한다
2. 시스템은 전체 화면 오버레이를 페이드 인 애니메이션으로 표시한다
3. 시스템은 1.1 스케일에서 1.0으로 축소되는 애니메이션을 재생한다
4. 시스템은 외부 원을 2초에 360도 회전시킨다 (무한 반복)
5. 시스템은 중간 원을 1.5초에 역방향 회전시킨다 (무한 반복)
6. 시스템은 로켓 아이콘을 1.0 ↔ 1.1 스케일로 왕복 애니메이션한다
7. 시스템은 타이틀에 Shimmer 효과를 적용한다
8. 시스템은 진행률 바를 0%에서 시작한다

#### 시나리오 2: 진행 단계 업데이트
1. 시스템은 3초마다 자동으로 다음 단계로 진행한다
2. 시스템은 현재 단계 텍스트를 업데이트한다:
   - 1단계: "블록체인 지갑을 확인하고 있어요"
   - 2단계: "암호화 키를 요청하고 있어요"
   - 3단계: "좌표를 암호화하고 있어요"
   - 4단계: "지갑 주소를 보호하고 있어요"
   - 5단계: "게임 참가를 완료하고 있어요"
3. 시스템은 진행률 바를 업데이트한다 (1/5 = 20%, 2/5 = 40%, ...)
4. 시스템은 단계 표시를 업데이트한다 (예: 3/5)
5. 시스템은 현재 단계 텍스트에 페이드 인 + 슬라이드 애니메이션을 적용한다

#### 시나리오 3: 로딩 오버레이 숨김
1. 시스템은 GameJoinLoadingOverlay.hide(context)를 호출한다
2. 시스템은 오버레이를 페이드 아웃 애니메이션으로 제거한다
3. 시스템은 300ms 대기한다
4. 시스템은 다음 화면(결과 오버레이)을 표시한다

### 5.3 시스템 동작

- 오버레이는 OverlayEntry를 사용하여 구현된다
- 사용자는 오버레이가 표시되는 동안 다른 UI와 상호작용할 수 없다
- 오버레이는 전체 화면을 덮으며 투명도 95%의 그라데이션 배경을 갖는다
- 애니메이션은 flutter_animate 패키지를 사용하여 구현된다

3. 시스템은 테두리 색상을 파란색(#4F46E5)으로 변경한다
4. 사용자가 이메일을 입력한다
5. 시스템은 입력된 텍스트를 표시한다

#### 시나리오 3: 비밀번호 입력
1. 사용자가 비밀번호 입력 필드를 탭한다
2. 시스템은 입력 필드에 포커스를 준다
3. 시스템은 테두리 색상을 파란색으로 변경한다
4. 사용자가 비밀번호를 입력한다
5. 시스템은 입력된 텍스트를 "••••••••" 형태로 마스킹하여 표시한다

#### 시나리오 4: 비밀번호 표시/숨김 토글
1. 사용자가 비밀번호 필드의 눈 아이콘을 클릭한다
2. 시스템은 _isPasswordVisible 상태를 토글한다
3. 시스템은 비밀번호를 평문으로 표시한다
4. 시스템은 눈 아이콘을 visibility_outlined로 변경한다
5. 사용자가 눈 아이콘을 다시 클릭한다
6. 시스템은 비밀번호를 다시 마스킹한다
7. 시스템은 눈 아이콘을 visibility_off_outlined로 변경한다

#### 시나리오 5: 유효성 검증 실패 (이메일)
1. 사용자가 이메일을 입력하지 않고 Login 버튼을 클릭한다
2. 시스템은 Form의 validate()를 호출한다
3. 시스템은 이메일 필드가 비어있음을 감지한다
4. 시스템은 이메일 필드 하단에 "Email is not valid" 에러 메시지를 표시한다
5. 시스템은 이메일 필드의 테두리를 빨간색으로 변경한다
6. 시스템은 로그인 프로세스를 중단한다

#### 시나리오 6: 유효성 검증 실패 (이메일 형식)
1. 사용자가 "@" 기호가 없는 이메일을 입력한다 (예: "test.com")
2. 사용자가 Login 버튼을 클릭한다
3. 시스템은 이메일에 "@"가 포함되지 않았음을 감지한다
4. 시스템은 "Email is not valid" 에러 메시지를 표시한다
5. 시스템은 로그인 프로세스를 중단한다

#### 시나리오 7: 유효성 검증 실패 (비밀번호)
1. 사용자가 비밀번호를 입력하지 않고 Login 버튼을 클릭한다
2. 시스템은 비밀번호 필드가 비어있음을 감지한다
3. 시스템은 비밀번호 필드 하단에 "Password is not valid" 에러 메시지를 표시한다
4. 시스템은 비밀번호 필드의 테두리를 빨간색으로 변경한다
5. 시스템은 로그인 프로세스를 중단한다

#### 시나리오 8: 로그인 버튼 클릭 (성공)
1. 사용자가 유효한 이메일과 비밀번호를 입력한다
2. 사용자가 "Login" 버튼을 클릭한다
3. 시스템은 Form의 validate()를 호출한다
4. 시스템은 모든 필드가 유효함을 확인한다
5. 시스템은 Login 버튼을 CircularProgressIndicator로 교체한다
6. 시스템은 authProvider.notifier.signIn(email, password)를 호출한다
7. 시스템은 GraphQL signIn Mutation을 전송한다
8. 시스템은 서버로부터 JWT 토큰과 사용자 정보를 받는다
9. 시스템은 토큰을 로컬 스토리지에 저장한다
10. 시스템은 authProvider 상태를 업데이트한다
11. 시스템은 로그인 성공을 감지한다
12. 시스템은 다이얼로그를 닫거나 홈 화면으로 이동한다 (isDialog에 따라)
13. 시스템은 녹색 SnackBar를 표시한다: "로그인되었습니다"

#### 시나리오 9: 로그인 버튼 클릭 (실패)
1. 사용자가 잘못된 이메일 또는 비밀번호를 입력한다
2. 사용자가 "Login" 버튼을 클릭한다
3. 시스템은 유효성 검증을 통과한다
4. 시스템은 로딩 인디케이터를 표시한다
5. 시스템은 서버로 signIn 요청을 전송한다
6. 시스템은 서버로부터 에러 응답을 받는다 (예: "Invalid credentials")
7. 시스템은 로딩 인디케이터를 숨기고 Login 버튼을 다시 표시한다
8. 시스템은 빨간색 배경의 에러 메시지 박스를 표시한다
9. 시스템은 에러 메시지 박스에 "Login failed. Please check your credentials." 또는 서버 에러 메시지를 표시한다
10. 시스템은 에러 아이콘을 표시한다

#### 시나리오 10: Google 로그인 버튼 클릭
1. 사용자가 "Login with Google" 버튼을 클릭한다
2. 시스템은 SnackBar를 표시한다: "Google login coming soon"
3. 시스템은 실제 Google 로그인을 수행하지 않는다 (TODO)

#### 시나리오 11: Sign Up 링크 클릭
1. 사용자가 "Sign Up" 링크를 클릭한다
2. 시스템은 다이얼로그 모드인 경우 현재 다이얼로그를 닫는다
3. 시스템은 Future.microtask()를 사용하여 '/signup' 경로로 이동한다
4. 시스템은 회원가입 화면을 표시한다

#### 시나리오 12: Forgot password 링크 클릭
1. 사용자가 "Forgot password?" 링크를 클릭한다
2. 시스템은 다이얼로그 모드인 경우 현재 다이얼로그를 닫는다
3. 시스템은 Future.microtask()를 사용하여 '/forgot-password' 경로로 이동한다
4. 시스템은 비밀번호 찾기 화면을 표시한다 (구현 여부는 별도)

#### 시나리오 13: X 닫기 버튼 클릭
1. 사용자가 우측 상단의 X 버튼을 클릭한다
2. 시스템은 _handleClose() 메서드를 호출한다
3. 시스템은 다이얼로그 모드인 경우 Navigator.pop()을 호출한다
4. 시스템은 페이지 모드인 경우 context.go('/')로 홈으로 이동한다

### 7.3 시스템 동작

- LoginForm은 페이지와 다이얼로그 두 가지 모드로 사용 가능하다 (isDialog 파라미터)
- TextFormField는 Form의 GlobalKey를 사용하여 유효성 검증을 수행한다
- authProvider는 Riverpod의 AsyncNotifier를 사용하여 로딩, 성공, 에러 상태를 관리한다
- 로그인 성공 시 JWT 토큰이 로컬 스토리지에 저장되고 이후 모든 API 요청에 포함된다

## 8. 회원가입 화면 (Signup Screen)

### 8.1 화면 구성

- 상단에 "SIGN UP" 타이틀이 있다
- 우측에 X 닫기 버튼이 있다
- 3단계 프로세스 표시가 있다 (1/3, 2/3, 3/3)
- 각 단계별로 다른 입력 필드가 표시된다:
  - 1단계: 이메일, 비밀번호, 비밀번호 확인
  - 2단계: 이름, 전화번호
  - 3단계: 약관 동의 체크박스들
- 하단에 "Next" 또는 "Complete" 버튼이 있다
- 하단에 "Already have an account? Login" 링크가 있다

### 8.2 사용자 행동 시나리오

#### 시나리오 1: 회원가입 화면 진입
1. 사용자가 회원가입 링크를 클릭한다
2. 시스템은 회원가입 화면을 표시한다
3. 시스템은 "SIGN UP" 타이틀을 표시한다
4. 시스템은 1단계 화면을 표시한다
5. 시스템은 진행 표시를 "1/3"로 표시한다

#### 시나리오 2: 1단계 - 이메일 및 비밀번호 입력
1. 사용자가 이메일 입력 필드에 이메일을 입력한다
2. 사용자가 비밀번호 입력 필드에 비밀번호를 입력한다
3. 사용자가 비밀번호 확인 필드에 같은 비밀번호를 입력한다
4. 사용자가 "Next" 버튼을 클릭한다
5. 시스템은 입력 필드의 유효성을 검증한다
6. 시스템은 모든 필드가 유효함을 확인한다
7. 시스템은 2단계 화면으로 전환한다
8. 시스템은 진행 표시를 "2/3"로 업데이트한다

#### 시나리오 3: 비밀번호 불일치 에러
1. 사용자가 비밀번호에 "password123"을 입력한다
2. 사용자가 비밀번호 확인에 "password456"을 입력한다
3. 사용자가 "Next" 버튼을 클릭한다
4. 시스템은 두 비밀번호가 일치하지 않음을 감지한다
5. 시스템은 비밀번호 확인 필드 하단에 "Passwords do not match" 에러 메시지를 표시한다
6. 시스템은 다음 단계로 진행하지 않는다

#### 시나리오 4: 2단계 - 개인정보 입력
1. 사용자가 이름 입력 필드에 이름을 입력한다
2. 사용자가 전화번호 입력 필드에 전화번호를 입력한다
3. 사용자가 "Next" 버튼을 클릭한다
4. 시스템은 입력 필드의 유효성을 검증한다
5. 시스템은 3단계 화면으로 전환한다
6. 시스템은 진행 표시를 "3/3"로 업데이트한다

#### 시나리오 5: 3단계 - 약관 동의
1. 시스템은 여러 개의 체크박스를 표시한다:
   - 전체 동의
   - 서비스 이용약관 동의 (필수)
   - 개인정보 처리방침 동의 (필수)
   - 마케팅 정보 수신 동의 (선택)
2. 사용자가 "전체 동의" 체크박스를 클릭한다
3. 시스템은 모든 하위 체크박스를 자동으로 체크한다
4. 사용자가 "Complete" 버튼을 클릭한다
5. 시스템은 필수 약관이 모두 동의되었는지 확인한다
6. 시스템은 회원가입 프로세스를 진행한다

#### 시나리오 6: 필수 약관 미동의 에러
1. 사용자가 필수 약관 중 하나를 체크하지 않는다
2. 사용자가 "Complete" 버튼을 클릭한다
3. 시스템은 필수 약관이 동의되지 않았음을 감지한다
4. 시스템은 에러 메시지를 표시한다: "필수 약관에 동의해주세요"
5. 시스템은 회원가입 프로세스를 중단한다

#### 시나리오 7: 회원가입 완료 (성공)
1. 사용자가 모든 단계를 완료하고 "Complete" 버튼을 클릭한다
2. 시스템은 Complete 버튼을 CircularProgressIndicator로 교체한다
3. 시스템은 authProvider.notifier.signUp()를 호출한다
4. 시스템은 GraphQL signUp Mutation을 전송한다
5. 시스템은 서버로부터 JWT 토큰과 사용자 정보를 받는다
6. 시스템은 토큰을 로컬 스토리지에 저장한다
7. 시스템은 자동으로 로그인 상태로 전환한다
8. 시스템은 홈 화면으로 이동한다
9. 시스템은 녹색 SnackBar를 표시한다: "회원가입이 완료되었습니다"

#### 시나리오 8: 회원가입 실패 (중복 이메일)
1. 사용자가 이미 존재하는 이메일로 회원가입을 시도한다
2. 시스템은 서버로 signUp 요청을 전송한다
3. 시스템은 서버로부터 "Email already exists" 에러를 받는다
4. 시스템은 로딩 인디케이터를 숨긴다
5. 시스템은 빨간색 배경의 에러 메시지 박스를 표시한다
6. 시스템은 "이미 가입된 이메일입니다" 에러 메시지를 표시한다
7. 시스템은 1단계로 돌아간다

#### 시나리오 9: Login 링크 클릭
1. 사용자가 하단의 "Already have an account? Login" 링크를 클릭한다
2. 시스템은 다이얼로그 모드인 경우 현재 다이얼로그를 닫는다
3. 시스템은 '/login' 경로로 이동한다
4. 시스템은 로그인 화면을 표시한다

#### 시나리오 10: 이전 단계로 돌아가기
1. 사용자가 2단계 또는 3단계에 있다
2. 사용자가 디바이스의 뒤로가기 버튼 또는 화면 상단의 뒤로가기 버튼을 클릭한다
3. 시스템은 이전 단계로 돌아간다
4. 시스템은 진행 표시를 업데이트한다
5. 시스템은 이전에 입력한 데이터를 유지한다

### 8.3 시스템 동작

- SignupForm은 StatefulWidget으로 구현되어 단계별 상태를 관리한다
- 각 단계는 별도의 Form을 가지며 독립적으로 유효성 검증을 수행한다
- 사용자가 입력한 데이터는 State 변수에 저장되어 단계 전환 시에도 유지된다
- 회원가입 완료 시 자동으로 로그인 처리되며 홈 화면으로 이동한다

## 10. 최적가 게임 목록 화면

### 10.1 화면 구성

- 배경은 deepWhite 색상이다
- 게임 카드들이 세로 리스트로 표시된다
- 각 카드는 수평 레이아웃이다 (이미지 좌측, 정보 우측)

### 10.2 사용자 행동 시나리오

#### 시나리오 1: 최적가 게임 목록 진입
1. 사용자가 홈 화면에서 "OPTIMAL" 탭을 클릭한다
2. 시스템은 OptimalGameListScreen을 표시한다
3. 시스템은 MockOptimalGameData.getAllGames()를 호출하여 게임 데이터를 가져온다
4. 시스템은 게임 카드 리스트를 표시한다

#### 시나리오 2: 최적가 게임 카드 표시
1. 시스템은 각 게임에 대해 다음 정보를 카드에 표시한다:
   - 좌측: 상품 이미지 (80x80, 12px 라운드)
   - 우측 상단: 게임 제목 (최대 2줄)
   - 우측 중간: 가격 범위 (예: "5만원 ~ 10만원") - Light 그라데이션 배경
   - 우측 하단: 참여자 수, 남은 시간, "최적가" 배지
2. 시스템은 "최적가" 배지를 Blue-Purple-Pink 그라데이션으로 표시한다

#### 시나리오 3: 가격 포맷팅
1. 시스템은 게임의 minPrice와 maxPrice를 가져온다
2. 시스템은 가격이 10,000 이상이면 "만원" 단위로 변환한다
   - 예: 50000 → "5만원"
   - 예: 55000 → "5.5만원"
3. 시스템은 가격이 10,000 미만이면 콤마로 구분한다
   - 예: 5000 → "5,000원"
4. 시스템은 포맷팅된 가격을 표시한다

#### 시나리오 4: 최적가 게임 카드 클릭
1. 사용자가 게임 카드를 탭한다
2. 시스템은 context.go('/optimal/{game.id}')를 호출한다
3. 시스템은 최적가 게임 상세 화면으로 이동한다

#### 시나리오 5: 이미지 로드 실패
1. 시스템은 게임 이미지 로드를 시도한다
2. 시스템은 이미지 로드에 실패한다
3. 시스템은 에러 빌더를 호출한다
4. 시스템은 회색 배경에 package 아이콘을 표시한다

#### 시나리오 6: 리스트 스크롤
1. 사용자가 화면을 위 또는 아래로 스크롤한다

4. 시스템은 부드러운 스크롤을 제공한다

## 부록: 공통 동작 정의

### A. 로딩 상태
- 시스템은 데이터 로딩 중 CircularProgressIndicator를 표시한다
- 로딩 인디케이터는 파란색(#5C72F5)이다
- 로딩 인디케이터는 화면 또는 컴포넌트 중앙에 위치한다

### B. 에러 상태
- 시스템은 에러 발생 시 빨간색 아이콘을 표시한다
- 시스템은 에러 메시지를 사용자에게 표시한다
- 시스템은 가능한 경우 "Retry" 버튼을 제공한다

### C. 빈 상태
- 시스템은 데이터가 없을 때 회색 아이콘을 표시한다
- 시스템은 "No data found" 또는 유사한 메시지를 표시한다
- 시스템은 필터 변경을 권장하는 안내 메시지를 표시한다

### D. 네비게이션
- 시스템은 GoRouter를 사용하여 화면 간 이동을 처리한다
- context.go()는 스택을 교체하는 이동이다
- context.push()는 스택에 추가하는 이동이다
- context.pop()은 현재 화면을 닫는다

### E. 상태 관리
- 시스템은 Riverpod Provider를 사용하여 앱 전체 상태를 관리한다
- ref.watch()는 상태 변경을 감지하고 UI를 재빌드한다
- ref.read()는 상태를 한 번만 읽는다
- ref.invalidate()는 Provider를 리셋하고 재로드한다

### F. 애니메이션
- 시스템은 flutter_animate 패키지를 사용하여 애니메이션을 구현한다
- fadeIn(), slideY(), scale(), shake(), shimmer() 등의 애니메이션이 사용된다
- 애니메이션은 일반적으로 300-600ms 지속된다
- 오버레이 애니메이션은 순차적으로 실행되어 부드러운 경험을 제공한다
